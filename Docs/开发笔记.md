## 1. 编译与发布

### 1.1 编译

```powershell
cd RimForex\Source
dotnet build RimForex.csproj
```

构建后 DLL 自动复制到 `RimForex\Assemblies\RimForex.dll`（csproj 的
`CopyToModFolder`，`AfterTargets="Build"`）。

### 1.2 引用来源自动切换

| 环境 | 条件 | 引用来源 |
|---|---|---|
| 本机开发 | `Local.props` 的 `RimWorldDir` 能找到 `Assembly-CSharp.dll` | 游戏目录的**真程序集** |
| CI / 没装游戏 | 没配或路径不对 | NuGet [`Krafs.Rimworld.Ref`](https://github.com/krafs/RimRef) |

构建日志会打印 `引用来源: true/false`。

`Krafs.Rimworld.Ref` 是经 Ludeon 许可发布的**引用程序集**（剥掉方法体只留签名），
能编译但不能跑游戏，也不涉及版权内容再分发。

**`Local.props` 被 `.gitignore` 排除，每台机器一份**，不配也能编译。
它只有一条本机 Steam 库路径，**上传工坊前从 `Mods\` 副本删掉**（无害但不干净）。

### 1.3 「DLL 变了 ≠ 代码变了」

项目开启了可重现构建（`Deterministic` + `ContinuousIntegrationBuild`）：

> 同一提交 + 同一套引用程序集 → 逐字节相同的 DLL。

但有两个坑：

1. **DLL 内嵌构建时的提交哈希**（`AssemblyInformationalVersion` = `0.2.3+<40 位>`）。
   在哪个提交上构建，DLL 里就记着哪个提交。构建后又提交了别的东西，这个哈希就对不上，
   `git status` 会显示 DLL 已修改，其实代码没动。

2. **本地与 CI 引用不同**是刻意的。两者产出的 DLL 应当一致，
   `release.yml` 里有一步专门比对。

**发布时的正确做法**（0.2.3 已验证）：先提交源码 → 在该提交上重编 → 单独提交 DLL。
这样 DLL 里的哈希指向真正的源码提交。

**踩过的坑**：`release.yml` 原来是**先构建再比对**，而 csproj 的 `AfterTargets="Build"`
已经把新 DLL 拷进 `Assemblies/` —— 于是比的是同一次构建的两个副本，永远相等，
这条检查等于不存在。现在改成构建**前**备份仓库 DLL，构建后与备份比（V02）。

### 1.4 `About\PublishedFileId.txt` 不能丢

RimWorld 判断"这个 mod 已发布过"靠的是 `About\PublishedFileId.txt`，**不是 packageId**。
反编译确认：`ulong.TryParse(File.ReadAllText(path), out var id)`。

- 上传成功后游戏自己写入，内容是**纯数字、无换行**（当前 `3821636766`）
- **这个文件丢了，下次上传会新建一个重复条目**（已经发生过一次）
- 它被 `.gitignore` 排除（属于作者账号信息），但必须留在本地
- 部署时整文件夹覆盖会把它带过去 —— 前提是**工作区那份还在**

### 1.5 自动发布

打 tag 触发 GitHub Actions：构建 → 跑全部门禁 → 打包 → 发 Release。

产物是 zip，解压后即 `Mods\RimForex\` 的内容（不含 `Source/` 与 `Docs/`）。

### 1.6 作者的工作流（不要再提醒）

**删掉 `Mods\RimForex` 整个文件夹，再把工作区的整个文件夹复制进去。**
全量替换天然覆盖一切，所以"记得拷 DLL"这类提醒不需要。

### 1.7 CHANGELOG 格式（作者要求，2026-10-21 定）

四组都**按需使用**，顺序不变：

```
**新增**   新功能、新按钮、新选项
**修复**   明显不对的行为 —— 玩家能感知到"以前是错的"；UI 显示与交互的问题也归这里
**平衡**   真正的玩法规则或数值调整（阈值、概率、价格、倍率……），不是修 bug
**其他**   放不进上面三组的
```

> **每一组都是可选的。** 只写有内容的组，没有就**整组省略** ——
> 不要为了让格式看起来完整而硬凑数。0.2.3 就只有「新增」和「修复」两组。

**怎么分辨「修复」和「平衡」**：那东西**本来该是那样吗**？
- 不该 → 修复。例：预警每步都弹一次（这是 bug/体验缺陷，不是设计）
- 本来就该那样、只是你觉得数值不合适 → 平衡。例：强平线从 50% 调到 30%

**其它要求**：

- 只写玩家能察觉的变化。门禁脚本修复、存档字段、死代码清理、重构 ——
  一律不写（放进提交信息与本文件 §5）。
- 中英双语并列，英文用 `Added` / `Fixed` / `Balance` / `Other`。
- 一组通常 3~6 条，能合并就合并。
- 每条尽量写"以前是什么样、现在是什么样"，而不是只写"修了 X"。

#### ⚠️ 最重要的那条：相对**上一个已发布版本**，不是相对本次开发

> **读者只玩过上一个已发布版本。** 判据就是这一句：
> 「他能不能对上号？」

本版新增的功能，如果在本版开发过程中自己修过 bug，**那不算「修复」** ——
玩家在上个版本里根本没见过那个功能，无从"以前是错的"。

**0.2.4 犯过这个错（作者指出，2026-10-23）**：

| 我写的 | 为什么错 |
|---|---|
| 修复：终端断电后不能再从浮动盈亏窗平仓 | 0.2.3 **根本没有**悬浮窗平仓这个选项，它是 0.2.4 才加的 |
| 修复：点「最小值」后再改杠杆，保证金会跟着重算 | 0.2.3 的杠杆是**按钮**，没有滑块，也就没有这个跟随问题 |
| 修复：终端改成可搬运后主菜单报红字 | 可搬运本身是 0.2.4 的新增，玩家从没在正式版里见过那个红字 |

**正确归属**：前两条应该并进「新增」里，作为新功能的**行为描述**；
第三条**整条删掉** —— 它修的是从未发布过的东西，玩家不需要知道。

**所以写 changelog 前先做一件事**：把要写的每一条，拿上个发布版本的
`CHANGELOG` 对照一遍 —— 那个功能在上个版本里存在吗？
不存在 → 它是「新增」，不是「修复」。

> **⚠️ 0.2.4 的实际处置（2026-10-23）**：错误发布前就被作者发现，
> 他**直接在 Steam 工坊页面**改好了文案。所以：
>
> · **工坊上那份是正确的**，仓库里的 `CHANGELOG.md` 没有同步（作者说不必同步）
> · 两处从此不一致 —— **以后要引用 0.2.4 的文案，以工坊为准，别照抄仓库**
> · 我不该假设"磁盘上的文件"是唯一真相：作者可以直接改线上文案

## 2. 数值设计

### 2.1 点差（核心摩擦）

```
spreadRate = clamp(SpreadCoef × volatility^SpreadExponent + SpreadFloor,
                   SpreadFloor, MaxSpread)
ask = mid × (1 + spreadRate / 2)
bid = mid × (1 - spreadRate / 2)
```

点差按**名义仓位**在开平各收一次。**实际范围 0.098% ~ 0.166%**。

四条约束同时在拉扯：

```
防 churn（下限，∝ 波动率）：往返点差 > 0.7979 × 单步波动
开 100x（上限，与波动率无关）：往返点差 ≤ MaxSpreadImpactOnMargin = 0.35%
趋势可行（上限）：往返点差 ≤ 0.85 × 一整日期望波动 ≈ 0.95%
```

- `0.7979 = √(2/π)`：高斯**绝对值**的期望只有标准差的 0.8 倍。
  所以 churn 期望 = `0.7979 × 单步波动 − 往返点差`，必须恒为负。
- 现行参数下 churn 期望 −0.077% ~ −0.093%，全档为负。

**节奏与点差的关系（反直觉）**：单步波动 ∝ √步长，点差是线性的。
所以**放慢节奏必须加宽点差**，否则低波动档的机械交易会变成正期望。

> 历史坑：`60 → 600` tick 那次放慢时点差没跟着调，覆盖掉到 42%，
> 机械交易重新变成正期望。**改 `TicksPerStep` 或点差参数后必须重跑
> `Docs/verify_spread.py`。**

### 2.2 手续费

单边 **0.02%**（按名义仓位），单笔下限 **2 白银**，开平各一次。

名义仓位低于 1 万时被下限支配，相当于固定收费。
**手续费远小于点差**：20 万名义仓位的往返点差约 1225 白银，手续费才 80。

历史：0.2% → 0.002% → 0.02%（2026-10-15 定）。

### 2.3 杠杆安全上限

两个独立约束，取更紧的：

```
约束 1（开仓即死）：点差 × 杠杆 ≤ 0.35
                   → 杠杆 ≤ 0.35 / 点差
约束 2（被日波动打死）：强平距离 (1 − StopOut) / 杠杆 ≥ 0.28 × 日波动
                   → 杠杆 ≤ 0.7 / (0.28 × 日波动)
```

> ⚠️ 约束 2 的分子是 **`1 − StopOutFraction`**，不是 `StopOutFraction`。
> 从开仓到强平，可亏损的比例是 70%，不是 30%。
> **当 `StopOutFraction = 0.5` 时两者恰好相等**，所以这个错误被掩盖了很久；
> 改成 0.3 后它会静默把高波动品种的 100x 降档到 50x。`audit.py` 有检查钉住它。

现行结果（**1x ~ 100x 对全部档位开放**）：

| 档位 | 波动倍率 | 日波动 | 往返点差 | 点差约束 | 波动约束 | 取用上限 |
|---|---|---|---|---|---|---|
| Spacer | 0.30–0.40 | 0.49% | 0.098% | 357x | 510x | **357x** |
| Standard | 0.45–0.60 | 0.74% | 0.112% | 312x | 340x | **312x** |
| Medieval | 0.65–0.85 | 1.05% | 0.130% | 269x | 238x | **238x** |
| Tribal | 0.95–1.10 | 1.44% | 0.152% | 230x | 174x | **174x** |
| Raider | 1.15–1.25 | 1.68% | 0.166% | 211x | 149x | **149x** |

**代价（刻意的）**：`StopOutVolCoverage = 0.28` 意味着允许强平距离远小于一天波动。
100x 下强平距离只有 0.7%，在高波动档上基本等于"把钱送给平台"。
这是为了保住"梭哈百倍杠杆"的节目效果，**不要让 100x 变成不可用** ——
早期取过 `StopOutVolCoverage = 1.0 / 0.6`，把高波动档压到 20~50x，百倍杠杆形同虚设。

下单面板在**强平距离 < 日波动**时显示橙色高风险提示，写明具体数值。

### 2.4 强平与预警

| 阈值 | 值 | 含义 |
|---|---|---|
| `CriticalThreshold` | **0.45** | 健康度跌破它 → 弹预警窗并**强制暂停** |
| `StopOutFraction` | **0.30** | 健康度跌破它 → 强制平仓，退还剩余净值 |

**健康度 = 净值 / 初始保证金**。所以 0.45 ⇔ 浮亏 55%，0.30 ⇔ 浮亏 70%。

> ⚠️ 分母是 **`BaseMargin = margin − addedMargin`（初始保证金）**，
> 不是 `margin`。**强平判据、预警、K 线爆仓线三处必须同一标尺**，
> 否则追加保证金后会出现"界面显示健康度 60%、离预警线还很远"却被静默强平（R05）。

#### 预警防抖（2026-10-21）

```
Pnl >= 0                      → 复位
health > 0.55                 → 复位（脱离危险）
0.45 < health <= 0.55         → 什么都不做（滞回带）
health <= 0.45 且未提醒过      → 若过了冷却（2500 tick）→ 入队
health <= 0.45 且已提醒过      → 等复位
```

为什么要滞回：修好子步采样后每步采样从 1 次变 17 次，
而盘内桥在 ±0.3σ 上下摆 —— 100x 下折算到健康度是 **±2.3 个百分点**，
几乎每一步都穿越 0.45。没有滞回就是刷屏。

`warnedAtTick` **不持久化**，与 `criticalWarned` 同进退。
`ResetWarnState()` **故意不复位** `warnedAtTick` —— 否则"回到安全区→立刻跌回→再弹"能绕过冷却。

#### 爆仓与穿仓的心情

| 事件 | 档位 | 单层心情 | 叠加上限 |
|---|---|---|---|
| 爆仓（强平） | TierMarginCall | −20 | 3 |
| 穿仓（余额变负） | TierBlowUp | **−28** | **1（不叠加）** |

两者**双向互斥**：`SupersededBy` 同时映射 9→8 与 8→9。
原来只写了单向，穿仓先记、爆仓后记时会叠加成 −48（R07）。

### 2.5 跳空

| 档位 | 幅度（× 单步波动 σ） | 每游戏日概率（强度 t ∈ [0,1]） |
|---|---|---|
| 常规 | **3 ~ 9σ** | `0.01 + t² × 0.14` → 1% ~ 15% |
| 极端 | **14 ~ 34σ** | `0.0003 + t² × 0.0037` → 0.03% ~ 0.40% |
| 测试·极端 | **60 ~ 120σ**，固定向下 | 按钮触发 |
| 测试·常规 | **8 ~ 9σ**，方向随机 | 按钮触发 |

方向不偏（对数空间带均值回归），长期不会单边漂移。

**播报阈值**：`max(0.15%, 6σ × vol)`。

> ⚠️ 原来是写死的 **0.5%**。而常规跳空是 3σ~9σ，太空档最大只有 0.242%、
> 工业档 0.367% —— **这两个档位的常规跳空永远不可能播报**，
> 作者一度以为自己"从没遇到过普通跳空"。
> 另外记录条件是 `mult > 0`，把**所有向下跳空都写成了 0**（价格暴跌却无提示）。
> 两处都已修（R02 + 阈值重设计）。

**为什么只有极端跳空能造成穿仓**：跳空不算罕见，但"跳空到大客户倒欠钱"是真尾部事件。
只用一档大跳空，实测会变成"每次强平都是穿仓"（每 1~2 游戏日一次）——
那不叫风险，叫必然。

## 3. 实现要点

### 3.1 时间：一律引用原版常量

```
TicksPerDay  = GenDate.TicksPerDay  = 60000
TicksPerHour = GenDate.TicksPerHour = 2500
TicksPerRealSecond = 60（1x）
```

> **这一条是踩出来的**：曾经自己推 `TicksPerDay = 3600`（"24 × 150"），
> 差了 **16.67 倍**。后果非常具体：整日边界判定写成 `abs % 3600 == 0`，
> 而真实一天 60000 tick —— **一个游戏日里这个条件会命中 16.7 次**，
> 结算事件满世界乱跳。倒计时也错了三次。
>
> 教训：**凡是原版已经定义的时间常量，就不该自己推。**

### 3.2 汇率模型：多尺度均值回归堆栈

五级 OU 叠加（τ 单位：游戏日）：

| τ | 角色 | σ_k/σ_step | 占预算 |
|---|---|---|---|
| 2 小时 | 点差 / churn 依赖的噪声底 | 0.079 | 0.6% |
| 8 小时 | 盯盘看到的分钟级往复 | 0.158 | 2.5% |
| 1 日 | 可交易的波段 | 0.273 | 7.5% |
| 3 日 | 趋势 | 0.473 | 22.4% |
| 9 日 | 大级别方向 | 0.819 | 67.1% |

**唯一必须守住的不变式**：

```
Σ_k  2σ_k²/(2−θ_k)  =  σ_step²  =  DailyVol² / StepsPerDay
```

把预算按尺度重新分配，**总量一个字节都不多**。所以日波动率恒为 `DailyVol`，
点差 / churn / 杠杆上限等经济验收的依据不变。实测误差 0.056%。

> 换掉"正弦锚"的原因：前三种加趋势的方案全部失败。
>
> | 方案 | 步级 σ 放大 | 死因 |
> |---|---|---|
> | 慢速 EMA 锚 | 1.0000 | θ/α 差 18 倍，锚每动一点价格 17 步内跟上抹平 |
> | 随机趋势项 | 1.14 ~ 4.6 | 均值回归把随机趋势吸收成噪声（≈17.7×） |
> | 锚做随机游走 | 1.0000 | gap 方差被 θ 锁死，价格只是「锚 + 固定偏移」 |
> | 确定性正弦 | 1.0006~1.0158 | 可用但**严格周期**，玩久了看出钟摆 |
>
> **根本矛盾**：随机过程里"步级噪声"与"窗口级趋势"由同一个 σ 绑定，
> 任何**随机**趋势项都必然抬高步级方差 —— 而那是 churn 验收的基石。
> 多尺度 OU 用**多级叠加**解决周期性，且计入方差预算。

**两个滑块**（慢周期行情强度 / 长度）控制最慢那一级的权重与 τ，
缩放后重新归一化 —— 只重排比例、不加总量。

> 这两个滑块**曾经是死的**：正弦锚被取代时删了调用点却留下设置项，
> 玩家拉滑块什么都不会发生。`audit.py` 有检查防止死控件复活。

### 3.3 盘内子步采样（R01 的教训）

每步内部再分 `SubSteps = 16` 个子步，**每推进一个子步就记一次路径点**。

```
TickStep()                        // 只建预算，不推进子步
    stepLogStart  = log(rate)
    stepLogTarget = stepLogStart + 高斯冲击 + 跳空 − 均值回归
    subStep = 0
AdvanceSubSteps(target)           // 随游戏时间推进
    while (subStep < target) { AdvanceSubStep(); AccumulateCandle(); }
AdvanceSubStep()
    log(rate) = 插值(start, target, k/16) + σ × OscAmp × 桥[k]
```

桥的两端都钉为 0，所以 `log(rate) @ k=16 == stepLogTarget` **逐点相等**，
步边界分布不受盘内路径影响。

> **R01 的坑**：`TickStep` 里曾经有一句 `for (k=0..15) AdvanceSubStep(c)`，
> 直接把 `subStep` 推到 16 —— 于是 `AdvanceSubSteps` 的 while 永远不成立，
> **采样一次都没执行过**，K 线影线只记到步边界那几个点。
> 而且那 16 次运算算完就被覆盖，纯属白算。
>
> 连带：修好之后每步采样从 1 次变 17 次，**预警立刻变成刷屏**（见 §2.4）。
> 这是"修一个 bug 暴露另一个"的典型。

**踩过的其它三个坑**（都记在 `AdvanceSubStep` 注释里）：

1. **每子步各抽 `σ/√N`**：方差看着对，但**均值回归被重复施加 N 次**，
   且子步间价格在变、`log(rate/anchor)` 跟着变，总量无法闭合。
   实测步边界标准差从 0.317 塌到 0.079（−75%）。
2. **单端桥**（只钉右端）：`B(1)` 带非零方差，而 K 线**开盘价**取自第一个子步，
   实体被系统性放大 7.9%（95% CI [1.061, 1.097]）。
3. **忘了在步边界补记采样点**：子步样本位于 `1/N…N/N`，第一个落在步**中间**，
   开盘价取错时刻，与坑 2 叠加成同样的 +9%。

**盘内路径池**：8 条两端钉零的布朗桥，按步轮换。
早先用全局唯一的静态桥，后果是**所有货币、所有 K 线的盘中路径完全相同** —— 影线纹理是假的。

### 3.4 K 线的三级周期

分K / 时K / 日K **各自独立聚合**，不是同一批数据换标签。
一根日K 横跨 333 个报价步，靠"每步存一根再合并"既费内存又要遍历 20 万个子步。

相位锚在**绝对游戏时间**上：`bucket = nowTick / periodTicks`，变了就封根。

好处：日K 每根从 0 时开始（与每日结算同相位）；
封根判据是"所属区间变了"而不是"差值 ≥ 周期"，低帧率下**不会漏根**。

**时K 的长度不随报价间隔滑块变化** —— 锚在 1 游戏小时上。

`MaxCandles = 100`（每级缓冲各自 100），图表最多画 101 根（含正在形成的那根）。
读档时会在 `PostLoadInit` 里重新裁剪（防御超量存档）。

**`GetCandles` 返回复用缓冲**：它被 `DrawCandles` 在 OnGUI 每一趟调用，
原来每次 new List + new 一根 K 线，图表开着时每秒上百 KB 垃圾。
现在复用 `viewBuf` / `viewLive`。**调用方只能当前帧使用、不要修改**。

### 3.5 盈亏与结算口径

```
Pnl = units × (markRate − entryRate)     做多
    = units × (entryRate − markRate)     做空      ← 方向必须翻转
```

> **曾经写成无方向的 `markRate − entryRate`**，后果是做空开仓瞬间白赚一个点差，
> "做空→平仓→做空→平仓"就是印钞机。
> 症状：做空时价格**上涨**反而盈利，盈利额恰等于 `点差 × 数量`。
> 实例：10000 单位 115.66→117.32，刷出 16631；修正后正确算出 −16600。
> `verify_spread.py` 的验收 9 锁死这个行为。

**权益 = 余额 + 占用保证金 + 浮动盈亏**（`FxAccount.Equity`）。

**当日盈亏 = 本次权益 − 上次权益**（`equityAtLastSettle` 存基线），
不是"此刻浮动盈亏"。

> 旧口径有两个硬伤：白天赚 5000 已平仓、午夜浮亏 2000 → 报"亏 2000"；
> 空仓时直接 `return`，**无论白天赚亏一律报 0**。
>
> 也不要用"已实现 + 浮动"两个累加器 —— 爆仓、追加保证金、穿仓这些路径
> 容易漏加或重复，**权益差天然自洽**。
>
> 另外权益口径里**必须含占用保证金**：曾经用 `余额 + 浮动盈亏` 算，
> 开仓那天会报出一笔等于保证金的假巨亏（`AccountEquity` 已删除，
> `audit.py` 检查它不会复活）。

**结算节奏**：`TicksAbs % GenDate.TicksPerDay == 0`（游戏内 0 时）且按日去重。
两道保险：`lastSettlementAbs` 硬下限（一游戏日最多一次）+ 首次进入把基准钉在未来。

**送信门槛**：`max(200, 净值 × 1%)`，平淡日静默累计，连续 3 个平淡日补一封摘要。
爆仓信不受限制。

### 3.6 交易历史与报告

`FxTradeRecord` 存的是**字符串快照**（`currencyName` / `pairLabel`）而不是引用，
所以删掉货币不会影响历史。上限 200 条。

**报告里的 `totalPnl` 是毛盈亏**（未扣手续费），净额要自己减 `totalFee`。
`pnl` 与 `units × (exitRate − entryRate)` 会有分位级差异（float 精度），**以 `pnl` 列为准**。

**历史里的 `spreadCost`**：写入时存的是开仓时真正被扣的那笔（`|units| × spreadAtOpen`）。
读档**不再重算** —— 早期版本用平仓中间价重算，价格一动数字就变
（1000 单位、开 100 平 110 时写入 112、重算得 123.2）。

> **已知遗留**：已经被旧版本改坏的那些记录停在错误值上。
> 技术上有办法还原（用 `entryRate` 反推开仓中间价，注意分母方向与用平仓价推算时相反，
> 幂等），但作者判断影响可忽略，**刻意不做**。

### 3.7 心情：按平仓，不按日

十档，阈值是**绝对白银数**（不随账户规模缩放，玩家能直接理解"亏了一万"）。

| 档位 | 区间 | 每层 | 时长 | 叠加上限 |
|---|---|---|---|---|
| 巨亏 | ≤ −10000 | −15 | 1.0 天 | 3 |
| 大亏 | −9999~−5000 | −10 | 0.85 天 | 3 |
| 中亏 | −4999~−1000 | −7 | 0.65 天 | 3 |
| 小亏 | −999~−1 | −5 | 0.5 天 | 3 |
| 小赚 | 1~999 | +3 | 0.5 天 | 3 |
| 中赚 | 1000~4999 | +5 | 0.65 天 | 3 |
| 大赚 | 5000~9999 | +8 | 0.85 天 | 3 |

挂满挤掉最早的那条。

**只作用于自由殖民者**（`IsFreeColonist`）。以前只判地图，
囚犯/访客/任务寄宿者都会共担殖民地盈亏 —— 已修。

> **`Thought.DurationTicks` 只对 `Thought_Memory` 生效**。

**文案的硬约束**：这些描述会被单独喂给 LLM 对话模组，所以每条必须**自带完整语境**
（点明外汇、方向、量级），否则 LLM 会理解成"殖民者想买沙发"。

## 5. 历史记录

### 5.1 踩过的坑（改这个 Mod 时请注意）

1. **🔴 不持久化的运行时字段，默认值必须"安全"** —— 迄今最严重的回归。

   `stepLogStart` / `stepLogTarget` 每步现算、**不进存档**，读档后回到 `0`。
   而 `rate = Clamp(Exp(logMid + bridge))`，**`Exp(0) = 1`，`MinRate` 也恰好是 1**
   → 读档后第一次推进，所有货币瞬间被打到价格下限，再慢慢爬回来。

   时序上很容易漏：读档后**第一帧**安全（欠 0 个子步），**第二帧**欠 1 个子步就会调
   `AdvanceSubSteps`，此时还没有任何 `TickStep` 跑过。

   **修法**：`stepBudgetValid` 标志，在"写"和"用"两侧都设防。

   **通用教训**：新增运行时字段时先问"它的默认值代入公式会算出什么"。
   `0` 经过 `Exp()` 变 `1`、经过乘法变 `0`、经过除法变 `∞` ——
   三者都可能落在合法区间内，**静默产生一个错误但看起来合理的价格**。

2. **Keyed 文本必须放 `Languages/<语言>/Keyed/`**，不能放 `DefInjected/Keyed/`。
   `DefInjected` 下每个子目录名都会被当作 Def 类型解析，`Keyed` 不是 Def 类型。

3. **占位符可以按语序重排**（中文用 `{1} {0}` 合法），但集合必须与调用方一致。

4. **中文字形在 `GameFont.Tiny` 下会超出标称行高**，被 Rect 纵向裁掉。
   悬浮窗曾经因此把"浮动盈亏"四个字切了一半 —— 改用 `GameFont.Small` +
   单行布局 + `Text.LineHeight`。

5. **`Colorize` 富文本是能用的**。曾经因为持仓格里标签不生效就断言
   "8 位 RGBA 不被 Unity 接受"，那个归因是错的。

6. **采样挂在 `WorldComponentTick` 上**，暂停时天然不推进、加速时自动变密，
   不需要任何暂停检测代码。

7. **`Rand` 的种子栈是全局的**：`PushState` 后若中途抛异常而没 `PopState`，
   之后所有用到 `Rand` 的地方（包括别的 mod）都会拿到错乱的序列。四处都包了 `try/finally`。

8. **`List.RemoveAt(0)` 做环形缓冲在 100 元素量级完全够用**，
   不必上环形队列 —— 但要知道它是 O(n)。

### 5.2 死代码清理记录

不要"重新发明"下面这些东西，它们都被删过：

| 项 | 为什么是死的 |
|---|---|
| `FxAccount.lockedMargin` | 只声明 + 只存档，从不读写 |
| `FxAccount.AccountEquity` | 漏算占用保证金，用它会报假巨亏 |
| `FxPosition.IsUpToDate` | 无调用者 |

| `ColorizeBySign` ×2 | 两处重复实现，已抽到 `FxUiUtil` |
| `TrendAnchor` / `TrendPhaseOf` 等 | 正弦锚整套被多尺度 OU 取代 |
| `MeanReversion` / `BridgeAmp` | 被 OU 衰减项 / `OscAmp` 取代 |
| `DurationTicksFor` | 删 `DurationTicks` 覆写时的遗留 |
| `MoodStageFor` / `lastMoodStage` | 心情改按平仓记录后无人调用 |
| **`0Harmony` 引用** | 代码零使用，却指向 workshop 目录 —— 取消订阅就编译失败 |
| `MarginWarning.map` | 填了但没人读，每次预警白跑一遍全地图扫描 |
| `showChartNavHint` | 设置项还画着，但没有任何代码读它 |

**教训**：删调用点 ≠ 删干净，`deadcode.py` 要定期跑。
**死引用比死代码更危险** —— 它会让编译失败，而失败原因与代码无关。

**看着像死代码但不是**：
- `FxCurrency.isTribal` —— 旧存档兼容线索，`ResolveTier` 的第三级兜底
- `legacyTribal` / `legacyVol` —— `Scribe_Values.Look` 的向后兼容读取
- `FxMarket.keyBuffer` —— 复用缓冲，避免每步分配
- `Clamp` / `Log` / `Exp` —— 刻意用 `System.Math`（double）而非 `Mathf`（float），
  对数空间随机游走对精度敏感

### 5.4 仍是缺口的东西

- **世界事件影响汇率**：目前只有随机游走，没有"政变/战争/丰收"冲击特定货币
- **货币作为交易媒介**：现在货币只是汇率标的，不能拿去跟派系买东西
  （要落地需要 `ThingDef` + `ITrader`，或扩展 1.6 的 `TradeCurrency` 枚举 —— 后者要 Harmony）
- **多空对冲与持仓合并**：同一货币的多个持仓是独立行，不自动净额合并
- **隔夜利息**
- **图表十字光标**（目前只有最新价横线）
- 波动率恒定、没有聚集效应（`VolOfVol = 0` 时关闭）
