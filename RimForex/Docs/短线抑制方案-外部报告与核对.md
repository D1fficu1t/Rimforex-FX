## §0 报告原文存档

### 一、问题诊断

当前模组采用无摩擦瞬时成交，短线收益过高的根本原因是：

- 手续费：费率 0.002%，单笔下限 2 白银，开平各一次，往返约 4 白银。
- 汇率更新：每 60 tick（1 游戏时）一步，单步波动约 0.18%（日波动 1.4% ÷ √60）。
- 杠杆：最高 100x，盈亏按敞口放大。
- 成交：瞬时，无点差、无延迟、无滑点。

以 100,000 敞口为例：
- 往返手续费 ≈ 4 白银，占敞口 0.004%。
- 单步波动 0.18%，占敞口 180 白银。
- 100x 杠杆下，保证金约 1,000 白银，单步波动 = 保证金 18%，手续费仅占保证金 0.4%。

结论：**手续费形同虚设，短线几乎无摩擦，期望收益显著为正。**

### 二、设计目标

1. 让短线交易的**往返成本 ≥ 单步平均波动**，使无脑高频刷钱期望为负或接近零。
2. 保留长线趋势交易的可玩性，长线抓 3%–10% 波段仍能盈利。
3. 成本按**敞口**计收，利用杠杆天然放大短线成本占保证金的比例。
4. 不修改原版交易逻辑，继续纯增量设计。

### 三、机制清单（按优先级）

| 优先级 | 机制 | 核心作用 |
|---|---|---|
| P0 | 买卖价差（Spread） | 每笔往返固定成本，直接吃掉短线利润 |
| P0 | 执行延迟（Execution Delay） | 成交价与看到的价格脱钩，无法精确抓顶摸底 |
| P1 | 滑点（Slippage） | 大单成本非线性增加，抑制重仓短线 |
| P1 | 锚价漂移（Anchor Drift） | 均值回归目标不可精确预测，消除确定性套利 |
| P2 | 隔夜利息（Overnight Interest） | 持仓时间成本，抑制长期等回归 |
| P2 | 流动性上限（Liquidity Cap） | 单步最大成交敞口，防止无限量短线 |

建议实施顺序：**P0 → P1 → P2**。先做 Spread + Delay，测试短线是否被压住，再逐步加码。

### 四、详细机制规格

#### 4.1 买卖价差（Spread）

**原理**：显示中间价，成交用买入价/卖出价。买入价高于中间价，卖出价低于中间价。

**公式**：
```
mid = 当前中间价
spreadRate = 基准点差 × 该货币波动倍率
ask = mid × (1 + spreadRate / 2)   // 买入价
bid = mid × (1 - spreadRate / 2)   // 卖出价
```

**参数建议**：
- 基准点差：单边 0.05% 起步，不够则加到 0.1%。
- 高波动货币（袭击者、部落）乘以 volatility 倍率。
- 点差可按日波动率动态调整：`spreadRate = baseSpread × (1 + dailyVolatility × 2)`。

**实现位置**：
- `FxMarket` 增加 `GetAsk(currency)` / `GetBid(currency)`，返回基于 mid 的成交价。
- `FxPosition` 开仓用 ask（做多）或 bid（做空），平仓反向。
- `MarkToMarket()` 用对应方向的 bid/ask 计算浮动盈亏。
- 行情表和 K 线仍显示 mid，但下单面板必须明确显示 ask/bid。
- 下单面板显示：`买入价 / 卖出价 / 点差`，并计入"总计花费"。

**效果预估**：
- 单边 0.05% → 往返 0.1%，单步波动 0.18%，成本占比 56%。
- 单边 0.1% → 往返 0.2%，成本占比 >100%，短线期望为负。

#### 4.2 执行延迟（Execution Delay）

**原理**：市价单不立即成交，进入待处理队列，延迟若干 tick 后以当时价格成交。

**设计**：
- 新建 `PendingOrder` 类：`currency` / `direction` / `units` / `leverage` / `submitTick` /
  `executeTick = submitTick + DelayTicks`
- 玩家点击"做多/做空"时，不直接开仓，而是生成 `PendingOrder` 加入 `List<PendingOrder>`。
- 在 `WorldComponentTick` 中检查 `executeTick <= 当前tick`，执行成交。
- 成交价使用**执行时的中间价 ± 滑点**，而不是提交时的价格。
- 下单面板显示"预计延迟 X 游戏时成交"，并提示价格可能变动。

**参数建议**：
- `DelayTicks = 60`（1 游戏时）起步。
- 可随订单规模增加：`DelayTicks = 60 + units / 10000 * 30`，上限 300 tick。
- 高波动货币延迟更长：`DelayTicks × volatilityFactor`。

**效果**：
- 玩家看到价格 A，提交后 1 游戏时成交价可能是 B，短线抓顶摸底失效。
- 在快速波动时，延迟造成的滑点可能直接吃掉利润。

#### 4.3 滑点（Slippage）

**公式**：
```
slippageRate = baseSlippage × (orderNotional / liquidity) × volatilityFactor × random(0.5, 2.0)
成交价 = 中间价 × (1 ± slippageRate)
```
- 做多买入：`ask = mid × (1 + spread/2 + slippageRate)`
- 做空卖出：`bid = mid × (1 - spread/2 - slippageRate)`

**参数建议**：
- `liquidity = 500,000`（敞口），低于此不滑点。
- `baseSlippage = 0.0005`（0.05%）。
- `volatilityFactor` 用货币的 volatility 倍率。
- 随机因子 `random(0.5, 2.0)` 每次成交独立。

#### 4.4 锚价漂移（Anchor Drift）

**公式**（每日结算时更新）：
```
锚价 = 锚价 × (1 + 高斯(0, 0.002))
```
或更平滑：
```
锚价 = 锚价 × 0.99 + 当前价 × 0.01
```

**参数建议**：每日漂移标准差 0.2%（年化约 3.2%），或 EMA 系数 0.01。

**实现位置**：
- `FxCurrency` 已有 `anchorPrice` 字段。  ← **⚠ 见 §9 核对结论第 1 条**
- 在每日结算时更新。
- 注意：更新后要重新计算回归项，避免突变。

#### 4.5 隔夜利息（Overnight Interest）

**公式**：
```
每日利息 = 保证金 × interestRate      // 参数建议 0.0005
或
每日利息 = 敞口 × 0.0001 × leverageFactor
```

**参数建议**：`interestRate = 0.0005`（保证金的 0.05%）每日；或按敞口 0.01% 每日。

**效果**：长期持仓有成本，抑制"买了不管等回归"。对短线影响小，需与点差配合。
  ← **⚠ 见 §9 核对结论第 2 条：这条数值完全失效**

#### 4.6 流动性上限（Liquidity Cap，可选）

每个货币每 tick 最大成交敞口 = `maxLiquidity`（如 1,000,000），超出部分部分成交或拒绝。

### 五、参数总表

| 机制 | 参数 | 建议值 |
|---|---|---|
| 点差 | 基准单边 | 0.05%（不够加到 0.1%） |
| 点差 | 波动倍率 | 用现有 volatility |
| 延迟 | 基准延迟 | 60 tick |
| 延迟 | 规模延迟 | units/10000×30 tick，上限 300 |
| 滑点 | 基准滑点 | 0.05%（仅超流动性部分） |
| 滑点 | 流动性阈值 | 500,000 敞口 |
| 锚价漂移 | 日标准差 | 0.2%，或 EMA 0.01 |
| 隔夜利息 | 日利率 | 保证金 0.05%，或敞口 0.01% |
| 流动性上限 | 单步最大敞口 | 1,000,000（可选） |

**调参流程**：先只加 Spread(0.05%) + Delay(60tick) → 测短线期望是否 ≤0 →
不够则 Spread 提到 0.1% 或加滑点 → 长线被误伤则降利息/点差，改用延迟和滑点 →
最终目标：**平均短线往返成本 ≥ 单步平均波动**。

### 七、注意事项与陷阱（原文要点）

1. **点差按敞口计，不按保证金**。杠杆越高，点差占保证金比例越大，天然抑制高杠杆短线。
2. **成交价与显示价分离**。行情表显示 mid，下单面板必须同时显示 ask/bid。
3. **延迟队列要持久化**。`PendingOrder` 需写入 `ExposeData`，避免读档丢失。
4. **滑点随机种子**用 `Rand`，每次成交独立。
5. **锚价漂移不要突变**，用连续函数。
6. **隔夜利息不要导致穿仓**。利息不应让玩家负债。
7. **性能**：队列与持仓数量可控（通常 < 100），无需优化。
8. **文档同步**：更新 README 的「手续费」「K 线」小节。
9. **与 Vanilla Trading Expanded 兼容**：仍不修改原版交易。
10. **测试用例**：单步开平 100x 确认净盈亏 ≤0；长线 10 日抓 5% 波段确认盈利；
    大单 1,000,000 确认滑点显著；读档后待成交订单恢复。

### 八、一句话总结

> 给短线加上**点差 + 延迟 + 滑点**，让往返成本 ≥ 单步波动；给长线保留趋势收益。先做 P0，不够再加 P1/P2。

## §9 核对结论（动手前必读）

### ✅ 验证正确的部分

| 结论 | 核对结果 |
|---|---|
| 手续费形同虚设 | **正确**。100,000 敞口往返 4 白银 = 敞口 0.004% |
| `1.4%/√60 = 0.18%` | **精确**，实测 0.1807% |
| 点差 0.05% 单边 → 占单步波动 55% | **正确**（往返 0.10% ÷ 0.1807% = 55%） |
| 点差 0.1% 单边 → 成本 >100% 单步波动 | **正确**（218%） |
| 点差能天然抑制高杠杆 | **推理成立**。保证金 = 敞口/杠杆，所以"敞口×点差"占保证金的比例随杠杆线性放大 |
| 点差按敞口计而非保证金 | **正确，且是这份报告最有价值的一条** |
| 成交价/显示价分离 | **正确**，UI 必须同时显示 mid 与 ask/bid |
| 不修改原版交易 | **正确**，所有机制都在 `FxMarket` 内部 |

### ❌ 问题 1：`FxCurrency` 并没有 `anchorPrice` 字段

报告 4.4 写「`FxCurrency` 已有 `anchorPrice` 字段」。**实际不存在**（已 grep 全源码确认）。

锚价实际存放在 `FxMarket` 的**私有字典**里：

```csharp
private Dictionary<int, float> anchors = new Dictionary<int, float>();
```

影响：锚价漂移需要改 `FxMarket.anchors` 的更新逻辑（以及它的 `ExposeData`），
不是在 `FxCurrency` 上加字段。**动手前先确认改动点，否则会找错地方。**

### ❌ 问题 2：隔夜利息 0.05%/日 完全失效（这条最严重）

报告 4.5 声称效果是"抑制长期持仓、买了不管等回归"。实测这个数值**没有任何作用**：

| 杠杆 | 利息占敞口 | 需要多少天才能抵上"一天的波动"(1.4%) |
|---|---|---|
| 1x | 0.0500% | **28 天** |
| 5x | 0.0100% | **140 天** |
| 20x | 0.0025% | **560 天** |
| 100x | 0.0005% | **2800 天** |

根因：报告 §7 陷阱第 1 条自己说了"点差按敞口计，**不按保证金**"，
但 4.5 的利息却建议按**保证金**计，于是杠杆越高利息占敞口的比例越小——
**方向正好反了**。100x 下持仓 2800 游戏日才等于一天波动，这在 RimWorld 里等于永不生效。

修正方向（二选一）：
- 改成**按敞口**计息（与点差一致）：`利息 = 敞口 × dailyRate`。若取 `dailyRate = 0.1%`，
  则 1x 下 14 天、100x 下 14 天抵一天波动——注意按敞口计后**与杠杆无关**，
  这才是"持仓时间成本"应有的语义。
- 若坚持按保证金计，数值要提到 **保证金的 2%/日** 才勉强有感
  （20x 下仍需 14 天抵消一天波动）。

**建议直接放弃隔夜利息，改用点差**：点差是每笔往返的即时成本，效果确定、可验证、
UI 上也能解释清楚；而隔夜利息要调到很夸张才有效，还会误伤长线玩法（与设计目标 2 冲突）。

### ⚠️ 问题 3：P0 的「执行延迟」与用户既定偏好冲突

用户在 2026-10-15 明确说过：

> "这个每日结算我指的是世界事件，**交易不是实时的就没意义了**。"

报告把 Execution Delay 列为 **P0**，但它的效果本质上是"下单后强制等 1 游戏时（可选 300 tick）
才成交"——这在体感上就是一种**批处理**，与用户要求的"实时"直接冲突。

建议：
- **先只做点差**（P0 里的 Spread），它单独就能把短线成本推到 55%~218% 的单步波动，
  大概率已经足够。
- 执行延迟降级为**可选/后置**；若确实需要，把延迟压到 15~30 tick 以内，
  并且 UI 明确显示"预计成交时间"，而不是让人以为按钮失灵。
- **明天先跟用户确认**是否接受"下单有延迟"这件事，再决定要不要做。

### ⚠️ 问题 4：与「波动性全是 1」的已知 bug 有交互

我们已确认：`volatility` 字段在**老存档里缺失**，`Scribe_Values.Look` 会静默回退到默认值 `1`，
所以现在所有货币的波动倍率都显示 `x1.0`（详见上一轮排查结论）。

这会**直接影响点差参数**：报告 4.1 建议 `spreadRate = 基准点差 × volatility`，
但如果 `volatility` 恒等于 1，那所有货币的点差就会完全一样，
高波动货币该有的更宽点差**不会生效**。

**所以正确顺序是：先修波动性（改成从派系属性现算，不依赖存档字段），再上点差。**
反过来做的话，点差会以错误的倍率上线，之后还得重新调参。

### ⚠️ 问题 5：`PendingOrder` 持久化会踩同一个坑

报告 §7 陷阱第 3 条提醒了"延迟队列要持久化"，这点是对的。
但要注意：我们刚刚才在 `volatility` 上踩过"新增存档字段 → 老存档缺失 → 静默回退默认值"的坑。
新增 `PendingOrder` 的 `ExposeData` 时，**所有字段都要给合理的默认值并考虑老存档**，
否则读档后可能出现价格为 0、方向错误之类的静默异常。

## §10 明天开工的建议顺序

1. **先修波动性显示**（从派系属性现算，自愈老存档）——否则点差倍率是错的。
2. **只做点差**：单边 0.05% 起步，`spreadRate = baseSpread × volatility`。
   开仓吃 ask/bid、平仓反向、`MarkToMarket` 用对应方向估值。
3. **UI 同步**：下单面板显示 `买入价 / 卖出价 / 点差`，并计入"总计花费"；
   行情表与 K 线仍显示 mid（但要说明）。
4. **实测短线**：单步开平，确认往返成本 ≥ 单步波动（100x 下尤其要验）。
5. 若还不够，再加 **滑点**（P1）；**执行延迟前先向用户确认**是否接受。
6. **隔夜利息暂缓**，改用点差承担时间成本；若非要加，按敞口计息且重新调参。
7. 交易历史增加成本项展示（点差成本 / 手续费分别列出），让玩家看懂钱花在哪。

## §11 一句话总结

> 报告的**核心诊断和点差方案是对的**（点差按敞口计、天然抑制高杠杆，这条最有价值）；
> 但**隔夜利息数值完全失效**（方向反了，100x 下 2800 天才抵一天波动），
> **锚价字段引用了不存在的 `anchorPrice`**，
> **执行延迟与用户"交易要实时"的既定要求冲突**，
> 且**必须先修 `volatility` 恒为 1 的 bug，否则点差倍率全部失效**。
