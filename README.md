# Rimforex — 0.2.2

RimWorld 1.6 外汇交易模组。纯增量设计：**不修改原版任何交易逻辑**，因此与 Vanilla Trading Expanded
等经济模组不存在价格系统层面的冲突。

以 **MIT 协议**开源，见 [LICENSE](LICENSE)。

## 安装

1. 把整个 `RimForex` 文件夹复制到：
   `G:\SteamLibrary\steamapps\common\RimWorld\Mods\`
2. 启动游戏，在模组列表中启用 **Rimforex**。
3. 无需 Harmony / HugsLib 作为前置（本模组未使用 Harmony 补丁）。

目标路径应形如：
`G:\SteamLibrary\steamapps\common\RimWorld\Mods\RimForex\About\About.xml`

### ⚠️ 作者专用：`About\PublishedFileId.txt` 不能丢

RimWorld 判断「这个 mod 已经发布过」靠的是 `About\PublishedFileId.txt`，
**不是 packageId**（反编译确认：`ulong.TryParse(File.ReadAllText(path), ...)`）。
上传成功后游戏自己把条目 ID 写进去，内容是**纯数字、无换行**。

**这个文件一旦丢失，下一次上传就会在创意工坊里新建一个重复条目。**
它恰恰在 `About\` 里，而部署时人们习惯整个文件夹覆盖过去 —— 最容易被抹掉。

所以部署时二选一：

- **整文件夹复制**（文件会跟着走，最省心），或
- **只覆盖真正改过的文件**（`Assemblies\RimForex.dll`、`About\About.xml` 等）

它已被 `.gitignore` 排除（属于作者账号信息，不该进公开仓库），
但**必须留在本地文件夹里**。别人克隆仓库时没有它是正确的 —— 他们不是作者。

### 从 GitHub 获取

本仓库**包含编译好的 `Assemblies/RimForex.dll`**，所以克隆下来即可直接使用：

```powershell
cd G:\SteamLibrary\steamapps\common\RimWorld\Mods
git clone https://github.com/D1fficu1t/Rimforex-FX.git RimForex
```

以后更新只要在这个目录里 `git pull`。

> **为什么把编译产物也提交了**：它是二进制，本该像 `bin/obj` 一样忽略 ——
> 那样仓库会更干净，但别人克隆后必须先装 .NET SDK 自己编译。
> 对一个"给人玩"的 mod，这个门槛太高。权衡后选择接受每次构建产生一个约 100 KB 的二进制提交。
>
> 想改回不跟踪：在 `.gitignore` 里加 `Assemblies/*.dll`，
> 再 `git rm --cached Assemblies/RimForex.dll`。

## 编译

```powershell
cd RimForex\Source
dotnet build RimForex.csproj
```

构建后 DLL 会自动复制到 `RimForex\Assemblies\RimForex.dll`。

### 先配一下游戏路径（可选）

编译需要 RimWorld 的程序集。**本机装了游戏的话**，把游戏路径写进配置：

```powershell
cd RimForex\Source
copy Local.props.example Local.props
# 然后编辑 Local.props，把 RimWorldDir 填成你的游戏安装目录
```

填的是**目录本身**，例如：

```xml
<RimWorldDir>D:\SteamLibrary\steamapps\common\RimWorld</RimWorldDir>
```

判断填对没有：那个目录下应当能看到 `RimWorldWin64_Data` 文件夹。

> `Local.props` 已被 `.gitignore` 排除 —— 它每台机器都不同，不该进仓库。
> 不配也能编译，见下。

### 引用来源会自动切换

编译需要 RimWorld 的程序集。但有两种环境，`csproj` 会自动选：

| 环境 | 条件 | 引用来源 |
|---|---|---|
| **本机开发** | `Local.props` 里的 `RimWorldDir` 能找到 `Assembly-CSharp.dll` | 游戏目录里的**真程序集** |
| **CI / 没装游戏的人** | 没配，或路径不对 | NuGet 包 [`Krafs.Rimworld.Ref`](https://github.com/krafs/RimRef) |

构建时会在输出里打印实际用了哪条路：

```
引用来源: true   (true=本机游戏, false=NuGet 引用程序集)
```

**为什么能这么切换**：`Krafs.Rimworld.Ref` 是**经 Ludeon 许可发布**的**引用程序集** ——
把方法体剥掉、只留下签名。编译器需要的类型信息一样不少，
但它既不能用来运行游戏，也不涉及版权内容的再分发。

选用的版本号（当前 `1.6.4871`）与 `About/About.xml` 里的目标游戏版本对齐。

### 关于「DLL 变了 ≠ 代码变了」

本项目开启了**可重现构建**（`Deterministic` + `ContinuousIntegrationBuild`）。
含义：

> **同一个 git 提交 + 同一套引用程序集 → 逐字节相同的 DLL。**

这条不变量有用，因为它把"二进制变了"和"真的改了代码"绑定在一起。
但有两个细节必须知道，否则会被误导：

1. **DLL 里嵌着源码的提交哈希。**
   `ContinuousIntegrationBuild` 会把 `AssemblyInformationalVersion` 写成
   `1.0.0+<40 位提交哈希>` 的形式。所以**你在哪个提交上构建，DLL 里就记着哪个提交**。
   构建之后又提交了别的东西，这个哈希就对不上了 —— 这会让
   `git status` 显示 DLL 已修改，其实代码一个字没动。

2. **本地与 CI 的引用不同**，但这是刻意的。
   CI 走 NuGet 引用程序集，本机走游戏真程序集。
   两者产出的 DLL 应当一致 —— `release` 工作流里有一[步](.github/workflows/release.yml)
   专门比对并打印，不一致时告警（不直接失败，因为跨提交的差异是正常的）。

**实践建议**：改完代码 → 构建 → 跑门禁 → `git add -A && git commit`。
让 DLL 与源码在同一个提交里，规则最简单。

### 自动发布

打一个 tag 就会自动构建、跑全部门禁、打包并发布 Release：

git push --tags
```

产物是一个 zip，解压后即为 `Mods\RimForex\` 的内容（不含 `Source/` 与 `Docs/`）。

## 玩法

### 建造 FX 交易终端

研究完 **电力（Electricity）** 后，在 **生产** 分类下可建造 **FX trading terminal**。

材料：钢铁 90 / 工业组件 4 / 白银 150，耗电 250W。
需要通电才能使用（断电时"打开外汇终端"按钮置灰）。

### 打开交易界面

选中终端 → gizmo 按钮 **Open FX terminal**。

界面分五块，每块严格裁剪到自己的 Rect，不会互相压盖。全部使用原版 `Widgets` 控件与配色。

- **账户区**：净值 / 可用保证金 / 占用保证金 / 浮动盈亏；**存入 / 提取输入框 + 按钮**；
  上次结算与累计手续费摘要。
- **行情表（左）**：所有派系货币的当前汇率、当日涨跌幅、当前持仓与盈亏。
- **K 线（右）**：当前选中货币的蜡烛图，**每格 = 1 游戏日**。
- **下单区**：保证金输入、杠杆档位、名义仓位 / 实际占用保证金 / 手续费明细、做多 / 做空；
  右侧持仓列表**每行带独立「平仓」按钮**。
- **底部时间控制条**：内嵌原版 `TimeControls`，**可以直接在窗口里改游戏速度**（含暂停）。

### 存取白银

不再是"一键全存/全禁"。账户区提供两个数字输入框：

- **存入**：填入要转入保证金账户的白银数量，`全部` 按钮一键填满当前地图可取用量，
  然后点 `存入`。只统计**未被禁用**的白银堆。
- **提取**：填入要取回的数量，`全部` 按钮填入当前余额可兑数量，然后点 `提取`。
  白银会以掉落物形式出现在终端旁。

### 保证金与杠杆（重要）

现在下单面板**输入的是保证金**，所以杠杆的作用是直接的：**押同样的钱，杠杆越高仓位越大。**

| 公式 | 含义 |
|---|---|
| `名义仓位 = 保证金 × 杠杆` | 这笔押金能撬动的市场规模 |
| `数量 = 名义仓位 ÷ 成交价` | 换算成整数单位（向下取整） |
| `实际占用保证金 = 数量 × 成交价 ÷ 杠杆` | 真正扣除的金额，通常略低于输入值 |

固定投入 114 白银为例：

| 杠杆 | 名义仓位 | 可开数量 | 1% 行情下的盈亏 |
|---|---|---|---|
| 1x | 114 | 1 | ±1.14 |
| 10x | 1,140 | 10 | ±11.4 |
| 50x | 5,700 | 50 | ±57 |
| 100x | 11,400 | 100 | ±114 |

**代价在风险**：杠杆 100x 时，价格反向波动约 **0.5%** 就会触及强平线（净值跌到保证金 50%）；
1x 时同样的波动只亏掉保证金的 0.5%。

> 早期版本输入的是「数量」而不是保证金，那时改杠杆只会改变押金、仓位纹丝不动，
> 很容易让人以为"加了 10 倍杠杆敞口却没变"。术语也一并调整：
> 旧的「敞口」现在叫「**名义仓位**」。

### 买卖价差（核心摩擦）

行情表与 K 线显示的是**中间价（mid）**，但成交吃的是买/卖价：

```
spreadRate = clamp(SpreadCoef × volatility^SpreadExponent + SpreadFloor,
                   SpreadFloor, MaxSpread)
ask（买入价） = mid × (1 + spreadRate / 2)
bid（卖出价） = mid × (1 - spreadRate / 2)
```

- **做多**开仓吃 ask、平仓吃 bid；**做空**开仓吃 bid、平仓吃 ask。
- 点差按**名义仓位**计收，所以杠杆越高，点差占保证金的比例越大 —— 高杠杆短线天然被抑制。
- 持仓的 `markRate` 存的是"按本仓方向现在平仓能拿到的价"，
  所以浮动盈亏**已经把点差算进去了**，是真正能落袋的数字。

| 参数 | 值 |
|---|---|
| `SpreadCoef`（缩放系数） | **0.08%** |
| `SpreadExponent`（缩放指数） | 1.0 |
| `SpreadFloor`（往返下限，= 单边 0.035%） | **0.07%** |
| `MaxSpread`（往返上限） | 3% |

**实际范围 0.098% ~ 0.166%**，随波动率档位变化 —— 低波动品种交易成本明显更低。

> **2026-10-16 整体下调点差。** 旧参数（`Coef=0.0003, Floor=0.003`）让点差落在
> 0.31%~0.34%，而且被地板主导、几乎不随品种变化。问题出在这个比值：
>
> ```
> 回本需移动 / 强平距离 = 点差 / StopOutFraction = 点差 / 0.5
> ```
>
> 它**与杠杆无关**（点差和强平距离都 ∝ 1/杠杆），所以 100x 下必须走完
> **63%** 的强平距离才回本 —— 风险预算几乎全被交易成本吃掉。
> 新参数把这个比值降到 **0.20 ~ 0.33**，顺带让点差重新对波动率有响应
> （地板占比从 89% 降到约 45%）。

#### 这组数字是怎么定出来的（重要）

点差同时被两个方向的约束夹击：

```
防 churn（下限，∝ 波动率）：往返点差 > 0.7979 × 单步波动
开 100x（上限，与波动率无关）：往返点差 ≤ 0.35%
趋势可行（上限，与波动率无关）：往返点差 ≤ 0.85 × 一整日期望波动 = 0.95%
```

`0.7979` 是高斯绝对值的期望系数（`√(2/π)`）—— 单步波动的**标准差**是 σ，
但期望的**绝对**移动只有 `0.7979σ`。所以判据是
`churn 期望 = 0.7979 × 单步波动 − 往返点差 < 0`，
实测 **−0.077% ~ −0.093%**，全档为负。

**三条下限里最紧的是"防 churn"，上限里最紧的是"开 100x"。**
新参数（最大点差 0.166%）距两者都还有充分余量。

**波动 ∝ √步长，而点差是线性的。** 所以放慢节奏会让单步波动涨得比点差快：

| `TicksPerStep` | 现实间隔 | 单步波动（基准档） | 往返点差覆盖 |
|---|---|---|---|
| 60 | 1 秒 | 0.1807% | 128% ~ 550%（新点差） |
| 600 | 10 秒 | 0.5715% | 41% ~ 174% ❌ **低波动档压不住** |
| **180** | **3 秒** | **0.3130%** | **128% ~ 365%** ✅ 现行 |

> 历史上 `60 → 600` 那次放慢就踩了坑：点差没跟着调，覆盖掉到 42%，机械交易重新变成正期望。
> **下调点差后这个坑更容易踩** —— 10 秒间隔时 Spacer 档只剩 41%，会变成印钱机。
> 所以报价间隔滑块拉到 10 秒时，低波动品种的短线套利会重新变得可行。

**改 `TicksPerStep` 或点差参数后必须重跑 `Docs/verify_spread.py`。**

为什么趋势玩法能活下来：点差只付一次，而行情优势 ∝ 持有步数的开方，
摊到持有期上就被摊薄了。这也是"惩罚高频、奖励判断"能同时成立的原因。

#### 验收数据

| 档位 | 往返点差 | 单步波动 | 点差/单步波动 | churn 期望 | 100x 下点差占保证金 |
|---|---|---|---|---|---|
| Raider | 0.166% | 0.0921% | 180% | −0.0925% | 16.6% |
| Tribal | 0.152% | 0.0786% | 193% | −0.0893% | 15.2% |
| Medieval | 0.130% | 0.0575% | 226% | −0.0841% | 13.0% |
| Standard | 0.112% | 0.0403% | 278% | −0.0799% | 11.2% |
| Spacer | 0.098% | 0.0269% | 365% | −0.0766% | 9.8% |

（30000 次模拟，名义仓位 2,400,000，完美方向）

随机方向下则是全档负期望（验收 6）。

> **判据不是"点差 / 单步波动"的比值**，而是 `0.7979 × 单步波动 < 往返点差`
> （高斯绝对值的期望只有标准差的约 0.8 倍）。
> 最右列"点差 / 日波动"衡量趋势玩法是否可行：低波动档天然偏高
> （Spacer 一个游戏日只波动 0.39%，而点差地板就有 0.30%），
> **这是点差地板与防 churn 在低波动端不可兼得的结果 —— 这里选择保 churn**，
> 代价是最稳的品种做小波段会亏。

### K 线与报价节奏

**1x 速度下游戏是 60 tick/现实秒，所以 `60 tick = 1 现实秒`。** 这是理解全部节奏的钥匙。

原版的时间基准（取自 `RimWorld.GenDate`）：

| 常量 | 值 |
|---|---|
| `GenDate.TicksPerDay` | **60000** |
| `GenDate.TicksPerHour` | **2500** |
| `GenDate.HoursPerDay` | 24 |

| 量 | tick | 游戏时间 | 现实时间（1x） |
|---|---|---|---|
| 一次报价（`TicksPerStep`） | 180 | — | **3 秒** |
| 一根 K 线（`QuotesPerCandle = 6`） | 1080 | 约 26 游戏分钟 | 18 秒 |
| 一个"外汇日"（每日结算周期） | **60000** | 1 游戏日 | **约 16.7 分钟** |

- 报价每 **3 现实秒**变一次 —— 看得清，也不用久等。
- 每 **6 次报价**合成一根 K 线，各级缓冲各保留 **100 根**。
- 一个游戏日有 **333 个报价步**（60000 / 180）。
- **报价间隔与每根 K 线的报价数都是模组设置里的滑块**（1~10 秒、3~10 次），
  `TicksPerStep` / `QuotesPerCandle` 是运行时属性而非编译期常量。
- **改节奏不会改变日波动率**：波动按 `1/√StepsPerDay` 缩放，一天累计始终是 `DailyVol`。
  跳空概率也按"日频率"标定再折算到每步，所以两个旋钮互不干扰。
- 图表标题旁有「距下次报价 X 游戏时（Y 秒）」倒计时，与 K 线换根**同源**；
  账户区有「距下次结算 X 小时」。**两者都能在模组设置里关掉。**

#### 三级周期：分K / 时K / 日K

图表右上角（`重置视图` 左边）有 **时K** 与 **日K** 两个按钮。再点一次当前选中的按钮
就回到 **分K**（默认），所以不为它多占一个按钮位。

| 周期 | 每根覆盖 | 100 根的历史深度 | 需要的现实时间（1x） |
|---|---|---|---|
| **分K** | 由「每根K线由几次报价合成」决定，默认 6 次报价 ≈ 26 游戏分钟 | 约 **1.8 游戏日** | 0.5 小时 |
| **时K** | 1 游戏小时（`GenDate.TicksPerHour` = 2500 tick） | 约 **4.2 游戏日** | 1.2 小时 |
| **日K** | 1 游戏日（`GenDate.TicksPerDay` = 60000 tick） | 约 **100 游戏日** | 27.8 小时 |

**三级是各自独立聚合的，不是同一批 K 线换个标签。** 原因很实际：一根日 K 要横跨
333 个报价步，靠"每步存一根再合并"既费内存又要遍历 20 万个子步。所以三级各自维护
自己的"当前未完成 K 线"，共用同一串价格路径，互相自洽。

**相位锚在绝对游戏时间上**，不用"多少报价步"：

```
bucket    = nowTick / periodTicks      // 2500 或 60000
if (bucket 变了) → 封根
```

这样有两个好处，也是刻意的：

1. **日K 每根都从 0 时整点开始**，与每日结算同一相位，两者对得上。
2. **封根判据是"所属区间变了"，不是"差值 >= 周期"**。后者在低帧率下一帧跨过
   多个整数周期时会漏掉中间的根（K 线缺根）；前者不会。

> 时K 的长度**不随报价间隔滑块变化** —— 它锚在 1 游戏小时上。若改用"14 个报价步"
> 这种写法，"一小时"就会随玩家的节奏设置漂移，而且日K/时K 的相位也不再对齐。

历史深度是按 `MaxCandles = 100` 算的。图表最多画 **101 根**（100 根已封 + 1 根正在形成），
最后一根让玩家看到"本周期还没走完"的实时状态。
- 滚轮缩放（10~100 根）、**鼠标悬停在某根 K 线上显示其开高低收**、`重置视图` 按钮。
  > **中键拖动已移除（2026-10-16）。** 它一直没能真正工作 —— IMGUI 对中键的
  > `MouseDown`/`MouseDrag`/`MouseUp` 派发不可靠（中键按下后收不到 `MouseDrag`），
  > 换成直接轮询按键状态也一样，因为拖动期间窗口本身收不到事件。
  > 与其留着一个"看着有、用起来没有"的功能，不如删干净：死代码会让人误以为平移可用。
  > `Docs/audit.py` 已加检查防止它复活。之后重做拖动时倾向改用**左键**（IMGUI 对左键可靠）。

#### 步内子采样：影线为什么曾经是假的

一个报价步只抽**一个**高斯数、只产生**一个**价格点，而 K 线的 high/low 只在那一点上更新。
于是"影线"退化成"6 个离散价的极值"——蜡烛偏方块，长上影、锤子线、十字星这类依赖
"步内冲高回落"的形态**结构上不可能出现**。实测影线/实体只有 0.49。

现在每个报价步内部再细分 `FxMarket.SubSteps = 16` 个子步，每推进一个子步就记一次路径点。

**关键设计：子步只增加采样密度，绝不改变步边界位移。**

```
TickStep()                     // 步边界：一次算好【整步位移】
    stepLogStart  = log(rate)
    stepLogTarget = stepLogStart + 高斯冲击 + 跳空 − 均值回归
    for k in 1..16: AdvanceSubStep()   // 子步只负责把这段位移走完
```

`AdvanceSubStep` 用 **线性插值 + 布朗桥**：

```
log(rate) = 插值(stepLogStart, stepLogTarget, k/16) + σ × BridgeAmp × 桥[k]
```

桥的两端都钉为 0（`桥[0] = 桥[16] = 0`），所以

```
log(rate) @ k=16  ==  stepLogTarget
```

**这是逐点相等，不是同分布** —— 步边界的方差、跳空、均值回归全部原样保留，
`Docs/verify_spread.py` 的整套经济验收因此不受影响（实测 0 失败）。

> **这一步踩了三个坑，都记在 `AdvanceSubStep` 的注释里：**
>
> 1. **每子步各抽 `σ/√N`**：方差看着对（`N × (σ/√N)² = σ²`），但**均值回归被重复施加 N 次**，
>    且子步之间价格在变、`log(rate/anchor)` 跟着变，总量无法闭合。
>    实测步边界标准差从 0.317 塌到 0.079（−75%），等于把日波动率改小 4 倍。
> 2. **单端桥**（只钉右端）：`B(1)` 带上非零方差，而 K 线**开盘价**取自第一个子步，
>    于是实体被系统性放大 7.9%（12 组种子，95% 置信区间 [1.061, 1.097]，不含 1）。
> 3. **忘了在步边界补记一个采样点**：子步样本位于步的 `1/N … N/N` 处，
>    第一个样本落在步**中间**，开盘价取错时刻，又与坑 2 叠加成同样的 +9% 偏差。
>
> 现在的结果（同一条路径，粗采样 vs 细采样）：

| 桥幅度 | 影线放大 | 实体 |
|---|---|---|
| 0.0 | 1.123× | **完全相等** |
| **0.3（当前）** | **1.185×** | **完全相等** |
| 1.0 | 1.584× | **完全相等** |

实体在所有幅度下都完全相等 —— 这正是"步边界守恒"的直接证据。
桥幅度取 0.3：影线明显变长，同时避免 1x 速度下报价数字跳得眼花。

> **尚未解决（D3/D4）**：波动率恒定、没有聚集效应；均值回归时标偏短
> （冲击半衰期约 17 步 ≈ 1.7 游戏小时，短于一根 K 线的 1.8 游戏小时），
> 所以图表在几根 K 线以上的尺度上仍表现为"围绕固定锚点的区间震荡"，
> 趋势难以跨越多根 K 线持续。这两项需要引入状态机，属下一步工作。


#### 平仓解锁用绝对阈值，不用滚动比较

持仓要跨过一次报价才能平仓，判据是**开仓时一次性算好的**
`closableAtTick = openTick + TicksPerStep`。

早期用的是 `QuoteStepOf(openTick) < QuoteStepOf(now)` 这种"滚动比较"。
问题在于 `QuoteStepOf(openTick)` 会随着 `lastStepTick` 前进而变成负数，
而 `QuoteStepOf(now)` 在两次报价之间恒为 0 —— 一个依赖"两个都在动的量"的判据很脆弱。
绝对阈值只会在越过时从 `false` 变一次 `true`，**不可能来回翻转**。

未解锁时按钮直接显示剩余秒数（如 `1.2s`），tooltip 也写明「还需 X 秒」，
等待上限就是一个步长（现在 3 秒）。

#### 节奏与点差的关系（反直觉，但很重要）

**缩短步长会让点差相对更"重"，不是更轻。** 因为：

```
单步波动 ∝ √步长      （波动随时间开方增长）
点差     ∝ 步长⁰      （每笔固定比例，与步长无关）
```

所以 600 → 180 tick 之后，单步波动从 0.57% 降到 0.31%，而点差不变，
**往返成本对单步波动的覆盖从 95%~117% 升到 173%~213%** —— 对 churn 的压制反而更强。

反过来，**放慢节奏才必须加宽点差**（这正是上一轮 60 → 600 时踩的坑）。
`Docs/pacing_analysis.py` 有完整的权衡表。

#### 最小持仓与平仓按钮

持仓必须跨过一次报价才能平仓。等待时间落在 `(0, TicksPerStep]` 之间，
平均约半个步长 —— 现在是 **1.5 秒左右**，不再让人以为按钮坏了。

未解锁时按钮直接显示剩余秒数（如 `1.2s`），tooltip 也写明「还需 X 秒」。

> 早期 `TicksPerStep = 600` 时这个等待长达 10 秒，而提示只写"还没跨过报价"
> 却不给剩余时间，看起来就像按钮永久失效。

> **倒计时曾经不准**：它用 `now % TicksPerStep` 算，而汇率推进用
> `now - lastStepTick >= TicksPerStep` 累加 —— 两者相位不同，
> 于是 K 线会在倒计时归零之前就变化。
> 现在倒计时直接读 `lastStepTick`（`FxGameComponent.TicksUntilQuote`），与推进逻辑同源。

> 另一个概念坑：早期 `TicksPerStep = 60`，等于"1 游戏时 = 1 现实秒"，
> 报价每秒跳一次。改成 600 之后才发现**波动 ∝ √步长、而点差是线性的**，
> 步子迈大必然要求点差同步变宽 —— 详见下面「买卖价差」一节。

### 各派系货币的波动性不同

不同经济体的汇率稳定性差异通过 `FxCurrency.volatility` 体现。
它是**派生属性，不是存档字段** —— 由 `tier`（派系类型）与 `loadID` 确定性算出，
同一个派系任何时候算出来都一样：

| 派系类型 | 波动倍率 | 日波动 | 杠杆上限 | 说明 |
|---|---|---|---|---|
| 袭击者（`permanentEnemy`） | **1.15 – 1.25×** | 1.68% | **50x** | 战时经济，汇率最动荡 |
| 部落（科技 ≤ 新石器） | **0.95 – 1.10×** | 1.44% | **58x** | 以实物/贝壳计价，没有央行稳汇率 |
| 中世纪及以下 | 0.65 – 0.85× | 1.05% | **79x** | |
| 工业级 | 0.45 – 0.60× | 0.74% | **111x** | 基准，可上 100x |
| 太空级（Spacer 以上） | **0.30 – 0.40×** | 0.49% | **113x** | 成熟货币，最稳定，可上 100x |

行情表有 `波动` 列直接显示倍率（如 `x1.2`）。

**跨度是 0.30 – 1.25（约 4 倍）**，比早期版本的 0.45 – 2.8（约 6 倍）收窄了。
收窄的原因见上文「杠杆安全上限」：波动率高于约 1.28 的品种在数学上不可能开出 100x。
但**性格差异依然明显** —— Raider 的日波动是 Spacer 的 **3.4 倍**，杠杆上限差 **2.3 倍**。

**为什么不做成存档字段？** 它曾经是。结果是：字段缺失时 `Scribe_Values.Look`
会**静默回退到默认值**，导致所有货币的波动倍率都变成 `x1.0`，
并连带让点差倍率全部失效。改成派生之后，旧存档读进来也能自愈：

- `factionDefName` 存档 → 读档时用 `DefDatabase<FactionDef>` 反查档位
- 兜底：用 `factionLoadID` 从 `FactionManager` 找派系
- 再兜底：旧存档的 `isTribal` 布尔值（历史字段，只读不写）

#### 慢周期行情：让图上真的能看出趋势

上面那张表的"4 倍差异"在**数据上完全成立**（实测 101 根 K 线的可见幅度之比是 3.86，
与 4.00 吻合），但**肉眼几乎看不出来**。原因不在波动率，而在两件事：

1. **可视窗太短**：101 根分K 只有 1.82 游戏日。窗内"总幅度 / 单根振幅"恒为 **10.8×**
   —— 不管哪个档位，图上都是一团等幅锯齿，只有标尺在变。
2. **锚价从不移动**：锚只在建币时设一次。而当时的均值回归强度让价格
   **17 步（1.7 游戏小时）就回到锚**，比一根 K 线（1.8 游戏小时）还短。
   于是每个货币都只是在自己的开局价附近做噪声，**永远走不出一段趋势**。
   （那套单 OU 实现已被多尺度堆栈取代，见「[汇率模型](#汇率模型多尺度均值回归堆栈)」。）

**修法**：锚价按一个长周期正弦缓慢摆动。

```
锚(t) = 锚0 * exp( TrendAmp * sin(2*pi*t/T + phase) )
    T     = TrendPeriodDays（默认 6 游戏日）
    phase = 由 loadID 确定性派生，让各货币错开摆动
    t     = GenTicks.TicksGame（游戏 tick，暂停时冻结）
```

| 设置项 | 默认 | 范围 | 含义 |
|---|---|---|---|
| 慢周期行情强度 | 0.02（约 2%） | 0 - 0.08 | **0 = 关闭**，退回纯均值回归 |
| 慢周期长度 | 6 游戏日 | 1 - 60 | 半个周期约 3 日的单边行情 |

> **为什么必须用确定性正弦，而不是随机漂移** —— 这一条试错四次才定下来，记录在案：
>
> | 方案 | 步级 sigma | 趋势自相关 | 死因 |
> |---|---|---|---|
> | 慢速 EMA 锚 | 1.0000 | -0.0004 | theta/alpha 差 18 倍，锚每动一点，价格 17 步内就跟上抹平 |
> | 随机趋势项 | 1.14 ~ 4.6 | -0.035 | 均值回归把随机趋势吸收成噪声：稳态贡献 sigma_drift/(theta*sqrt2) 约 17.7 倍 |
> | 锚随机游走 | 1.0000 | -0.039 | 稳定后"价格-锚"的 gap 方差被 theta 锁死，价格只是「锚 + 固定偏移」 |
> | **确定性正弦** | **1.0006 ~ 1.0158** | **+0.05 ~ +0.125** | 可用 |
>
> **根本矛盾**：随机过程里"步级噪声"与"窗口级趋势"由**同一个 sigma** 绑定，
> 所以任何**随机**趋势项都必然抬高步级方差 —— 而那是点差/churn 经济验收的基石。
> 正弦锚每步的位移是确定的，**完全不给步级方差加东西**。

**代价（必须知情）**：可视窗内的总幅度会被放大。`amp=0.02` 约 2 倍、`amp=0.035` 约 3.7 倍。
幅度变大意味着**强平会更快发生**（强平距离是固定的 0.5%）。所以强度做成了滑块，可随时回调。

**churn 期望不受影响**：正弦漂移是**双向**的 —— 顺势步更易盈利、逆势步更易亏损，
期望上相互抵消。实测各幅度下 churn 均为 -0.131%，`verify_spread.py` 全部通过。

### 临近爆仓预警

健康度 = `持仓净值 / 原始保证金`。1.0 = 打平，0 = 保证金亏光。

| 触发点 | 行为 |
|---|---|
| 健康度 ≤ **0.60**（`CriticalThreshold`，浮亏 40%） | 弹出预警窗口并**强制暂停游戏** |
| 健康度 ≤ **0.50**（`StopOutFraction`，浮亏 50%） | **强制平仓**，退还剩余净值 |

数值依据与设计理由见上文「预警：一个阈值，一次弹窗」。

**暂停由窗口自己持有**（`Window_MarginCall.forcePause = true`），而不是靠一次性的
`TogglePaused()` 调用。这一点是踩坑换来的：

- 早期版本在 `WorldComponentTick` 里 `TogglePaused()`，但窗口没有 `forcePause`。
  结果是——暂停一发生，下一 tick 确实不跑了，**但窗口本身不持有暂停状态**，
  任何恢复时间的操作都会让 tick 重新跑起来，`MaybeWarn` 再把预警判为"健康度已恢复/已提醒"
  并清掉队列，窗口就被自动关闭了。表现就是"弹出来一秒就没了，而且时间没暂停"。
- 现在暂停与窗口的存在严格绑定：窗口在 → 暂停 → 下一 tick 不执行 → 健康度不变化
  → 预警不会被自动作废。
- 窗口呈现由 `WorldComponentOnGUI` 负责，**不依赖交易终端是否打开**。
- `PreClose()` 里统一清理预警条目，所以不管是点按钮、按 Esc 还是点 X 关闭，都不会留下残渣。
- 有 0.4 秒输入保护期（`InputGuardSeconds`）：触发预警的那次点击/按键不会立刻把窗口关掉。

#### 告警水位模型（修掉"无限弹窗"的那次改动）

早期版本里，玩家点「暂不处理」会把 `marginWarned` / `criticalWarned` 重置为 `false`，
于是**下一个 tick 的 `MaybeWarn` 立刻重新入队 → 窗口无限重弹**。
现在改成 `FxPosition.warnedHealth`（上次告警时的健康度，`-1` = 从未提醒）：

| 情形 | 行为 |
|---|---|
| 第一次跌破 25% | 提醒，并记下水位 |
| 玩家点「暂不处理」 | **只从队列移除，不动水位** → 不会立刻重弹 |
| 健康度继续跌到 `水位 × 0.6`（`RearmFraction`） | 更危险了，再提醒一次 |
| 健康度跌破 10% 爆仓线 | 强制提醒（每个持仓只强制一次） |
| 健康度回到 25% 以上 | `ResetWarnState()` 复位，将来再恶化会重新提醒 |

这样"别烦我"和"真危险了要叫我"两个诉求能同时满足。

预警窗口提供：

| 选项 | 效果 |
|---|---|
| **追加保证金** | 从可用保证金划入该持仓。默认填 `min(余额, 原保证金)`，另有 `全部` 和 `补到安全线`（自动算出把健康度拉回 25% 所需的最少金额），也可自己填。补到安全线以上会复位告警水位。 |
| **暂不处理** | 关闭窗口，让平台在保证金亏光时自行强平。 |

- 行情反弹回安全区会自动作废已排队的预警。
- 追加保证金用 `addedMargin` 单独记录，健康度分母始终是**原始保证金**。

### 手续费

| 参数 | 值 |
|---|---|
| 费率 | **0.02%**（`FeeRate = 0.0002`），按**名义仓位**计收 |
| 单笔下限 | **2 白银**（`MinFee`），开平各计一次 |

| 名义仓位 | 单边手续费 | 往返 |
|---|---|---|
| 11,633 | 2.33 | 4.65 |
| 100,000 | 20.00 | 40.00 |
| 200,000 | 40.00 | 80.00 |
| 1,000,000 | 200.00 | 400.00 |

- 名义仓位低于 1 万时手续费被下限支配，相当于**固定收费**（真实平台也是"最低 2 元"）。
- **手续费远小于点差**：20 万名义仓位的往返点差约 **1225 白银**，手续费才 80。
  所以玩家的主要摩擦来源是点差，手续费只作为"平台抽成"存在。
- 点差与手续费是**两项独立成本**，下单面板与交易历史都分列显示。

> 历史沿革：最早是 0.2%（太贵，往返约为名义仓位的 0.4%），后来降到 0.002%
> （几乎没有存在感），2026-10-15 定在 **0.02%**。

### 下单面板：输入的是保证金，不是数量

**输入你愿意押多少钱，杠杆决定这笔钱能撬动多大仓位。** 这是杠杆的本意。

```
输入保证金 M，选定杠杆 L
  → 名义仓位 = M × L
  → 可开数量 = floor(名义仓位 ÷ 成交价)     ← 单位必须是整数
  → 实际占用保证金 = 可开数量 × 成交价 ÷ L
```

**单位取整的后果**：实际占用的保证金通常略低于你输入的金额，**差额不会被扣**。

例（成交价 114，10x 杠杆，输入 120 保证金）：

| 项 | 值 |
|---|---|
| 每单位需保证金 | 11.4 |
| 可开数量 | **10 单位** |
| 名义仓位 | **1140.0** |
| 实际占用保证金 | **114.00**（不是 120） |
| 未使用的部分 | 6.00，不扣 |
| 手续费 | 2.00 |

这样账目永远精确，不会出现"扣了钱但仓位对不上"。已用脚本验证：
在 6 档杠杆 × 多档保证金的组合下，**实际保证金超出输入金额的次数 = 0**，
且 `名义仓位 = 数量 × 成交价` 精确成立。

#### 面板字段

| 字段 | 含义 |
|---|---|
| **保证金** | 玩家输入。下限 = 开 1 单位所需的最少金额 |
| **杠杆** | 1 / 5 / 10 / 20 / 50 / 100x |
| 买入 / 卖出 / 点差 | 当前盘口 |
| 此仓位承担的点差成本 | `数量 × (ask − bid)` |
| 实际数量 | 由保证金反解出的整数单位数 |
| **名义仓位** | `数量 × 成交价`，这笔交易在市场里的实际规模 |
| 实际占用保证金 | 真正会从余额扣除的金额 |
| 手续费 | 名义仓位的 0.02% |
| 总计花费 | 实际占用保证金 + 手续费 |
| 可用保证金 | 账户可用余额 |

按钮：加减档 `±1 / ±10 / ±100 / ±1000`（单位：白银）、`梭哈`、
`最小值`（重置为"还能开 1 单位"的最小保证金）、`做多` / `做空`。

> **术语变更**：这里以前叫「数量」，输入的是单位数；「敞口」现在是「**名义仓位**」。
> 旧口径下改杠杆只改押金、不改仓位，容易让人以为"加了 10 倍杠杆敞口却没变"。
> 改成按保证金下单后，杠杆的作用就直观了：**押同样的钱，杠杆越高仓位越大。**

#### 资金校验

- 输入保证金的下限自动计算，永远不会低到开不出仓位。
- `梭哈` 用可用余额反解最大单位数，再折回所需保证金。
- 开仓校验 `实际占用保证金 + 手续费 ≤ 可用余额`。

### 每日结算只做"世界事件"

每 **1 游戏日** 触发一次，触发条件是**当前 `TicksAbs` 恰好落在整日边界上**
（`TicksAbs % GenDate.TicksPerDay == 0`，也就是游戏内时钟的 **0 时**），并且按日去重。

**不参与交易定价**（不影响买卖价、不改变行情推进），只负责：

1. 把当前价写进 `previousRate` 作为"昨日收盘价"，供行情表的日涨跌列使用。
   > 措辞订正：早先这里写"不参与交易定价"，容易被读成"不写任何状态"，
   > 但实际上 `AnchorDayOpen()` 确实会写入 `previousRate`。
   > 准确说法是：**它不改变定价，但会记录一个显示用的基准价。**
2. 统计当日盈亏，弹出结算信件（当天动过仓或盈亏过门槛才发，见下）。

> **⚠️ 结算不再挂心情（2026-10-17 改）。** 心情已改为**按单笔平仓**实时记录，
> 见「心情：按平仓，不按日」。结算现在只做"事件通告"。

### 当日盈亏怎么算：权益差，不是浮动盈亏

这是 2026-10-17 修掉的一个真 bug。**口径错了，但数字看着完全合理**，所以特别记下来。

```csharp
// ❌ 旧：只看"此刻持仓"的浮动盈亏
float dayPnl = acc.FloatingPnl;
if (acc.positions.Count == 0) { lastDayPnl = 0f; return; }
```

| 情形 | 旧口径 | 正确 |
|---|---|---|
| 白天赚 5000 已平仓，午夜浮亏 2000 | **亏 2000** | **赚 3000** |
| 白天赚 5000 全平，午夜空仓 | **0**（提前 return） | **赚 5000** |

第二种更糟：空仓时直接清零，**无论白天赚亏多少一律报 0**，连心情都不给。

**修法：当日盈亏 = 本次权益 − 上次权益**（`equityAtLastSettle` 存基线）。

```csharp
float dayPnl = acc.Equity - acc.equityAtLastSettle;   // 权益 = 可用余额 + 占用保证金 + 浮动盈亏
```

**为什么不用两个累加器**（一个记已实现、一个记浮动）：爆仓、追加保证金、穿仓这些路径
容易漏加或重复加；而**权益差天然自洽**，不会漂移。

**权益的口径里必须含"占用保证金"** —— 这里错过一次：曾经用一个
`AccountEquity`（= 可用余额 + 浮动盈亏）来算，但开仓时余额已经扣掉了保证金，
所以它少算了整笔占用保证金。结果是**开仓那天结算会报出一笔等于保证金的假巨亏**，
平仓那天则相反。正确口径与 UI 顶部"净值"、交易历史导出一致：`FxAccount.Equity`。

**旧存档兼容**：`equityAtLastSettle` 是新字段，首次结算若为 0 就补记基线（那天记为 0），
不会凭空报一个巨大数字。


> **这里错过两次，根因是同一个：我一直在自己推导"一天有多长"。**
>
> 第一次：判据是"越过即触发"（`if (TicksAbs < nextSettlementTick) return;`），
> 只要 `nextSettlementTick` 落后就会在**任意时刻**补结算。
>
> 第二次（真正的根因）：我写的 `TicksPerDay = 3600` 来自
> "24 游戏时 × 150 tick/时"这个**自己推的算式** —— 而原版根本不是这个数。
> 反编译 `RimWorld.GenDate` 得到的真实常量是：
>
> | 原版常量 | 真值 | 我错写的 |
> |---|---|---|
> | `GenDate.TicksPerDay` | **60000** | 3600 ❌ |
> | `GenDate.TicksPerHour` | **2500** | 150 ❌ |
>
> 差了 **16.67 倍**。后果非常具体：整日边界判定写成 `abs % 3600 == 0`，
> 而真实一天有 60000 tick —— **一个游戏日里这个条件会命中 16.7 次**，
> 于是结算事件在一天中到处乱跳。
>
> 现在全部直接引用原版常量（`GenDate.TicksPerDay` / `GenDate.TicksPerHour`），
> 原版改了我也跟着改。`Docs/audit.py` 会核对这两个引用。
>
> | TicksAbs | abs % 60000 | 小时 | 会结算? |
> |---|---|---|---|
> | 59999 | 59999 | 23 | 否（非边界） |
> | **60000** | **0** | **0** | **是** |
> | 60001 | 1 | 0 | 否（非边界） |
>
> 结算信件末尾会附上**结算时刻**（如"第 52 日 0 时"），
> 可以直接在游戏里核对它是否只在午夜跳出。

账户区右上角有一条 **`距下次结算 X 小时`** 倒计时 —— 周期对不对可以直接看着验证。

#### 两道保险

1. **`lastSettlementAbs` 硬下限**：`abs - lastSettlementAbs < TicksPerDay` 时直接跳过并重排。
   无论 `nextSettlementTick` 因为什么原因落后（读档残留、调试加速、字段缺失回退），
   都保证一个游戏日内最多结算一次。
2. **首次进入时把基准钉在未来**：新开局/首次读档时 `lastSettlementAbs` 初始化为
   `nextSettlementTick - TicksPerDay`，避免它停在 `int.MinValue` 导致跨过一个边界就立刻结算。

#### 为什么结算信件曾经"看起来"很频繁

送信门槛原本是固定 `|当日盈亏| ≥ 40 白银`。在 20 万级别的账户上，
一天的正常波动轻易就有几百银，于是**几乎每天都发一封信** —— 结算本身确实是一天一次，
但满屏的信件让人觉得"怎么一直在结算"。

现在门槛改为**按账户规模取相对值**：

```
threshold = max(200, 净值 × 1%)
```

- 达到门槛 = 重要日 → 发信
- 平淡日 → 静默累计，连续 **3** 个平淡日才补一封摘要（`quietDays`）

爆仓信件不受此限制，仍然实时发。

### 交易是实时的（重要）

**持仓估值与爆仓都是实时的，不等每日结算。**

- 每次汇率变动时，`MarkToMarket()` 立即把所有持仓的现价同步为最新汇率，
  账户的浮盈浮亏、净值、单笔持仓盈亏立刻反映行情。
- `CheckMarginCalls()` 在同一时刻检查爆仓 —— 保证金一亏光就强平，
  不会等到第二天才处理一个已经穿仓的仓位。
- 持仓列表每行显示：`货币 方向 单位数 开仓价 现价 杠杆`，右侧是 `盈亏（保证金）`。
- 做空同样实时：价格下跌 → 立即显示盈利。

### 开仓锁定期：盈亏保持为 0

**从开仓到跨过第一次报价之间，浮盈浮亏恒为 0**，不是立即显示一个负值。

原因：开仓价是 ask、平仓价是 bid，两者天生差一个点差。如果开仓瞬间就按 bid 估值，
盈亏会立刻显示 `-点差`，而健康度 = `(保证金 - 点差) / 保证金` ——
于是"一开仓就报警"，甚至在极高杠杆下**解锁瞬间直接被强平**。
这也与现实一致：平台给的是 0 点差的入场价，点差成本在建仓完成后才体现。

实现上，锁定期内把 `markRate` 冻结在 `entryRate`，所以 `PnL` 精确为 `0.000000`。
解锁时刻就是 `closableAtTick`，和平仓按钮解锁是同一个时间点，不会互相矛盾。

### 杠杆安全上限

杠杆受**两个独立约束**夹击，取更紧的那个：

```
约束 1（开仓即死）：点差 × 杠杆 ≤ 0.35
                    → 杠杆 ≤ 0.35 / 点差
约束 2（被日波动打死）：强平距离 0.5/杠杆 ≥ 0.28 × 日波动
                    → 杠杆 ≤ 0.5 / (0.28 × 日波动)
```

**结果：1x ~ 100x 对全部档位开放。**

| 档位 | 日波动 | 往返点差 | 点差约束 | 波动约束 | **取用上限** | 100x |
|---|---|---|---|---|---|---|
| Spacer | 0.49% | 0.098% | 357x | 364x | **357x** | 可用 |
| Standard | 0.74% | 0.112% | 312x | 243x | **243x** | 可用 |
| Medieval | 1.05% | 0.130% | 269x | 170x | **170x** | 可用 |
| Tribal | 1.44% | 0.152% | 230x | 124x | **124x** | 可用 |
| Raider | 1.68% | 0.166% | 211x | 106x | **106x** | 可用 |

**下调点差后，卡住杠杆的从"点差约束"翻转成了"波动约束"**：
低波动档由点差约束主导（357x），高波动档由波动约束主导（106x）。
无论哪一边，1x ~ 100x 都远在安全线内。

#### 代价：高波动档的 100x 仓位活不过一次报价

`StopOutVolCoverage = 0.28` 意味着允许**强平距离远小于一天波动**。
100x 下强平距离固定 0.5%，实测（每游戏日）：

| 档位 | 强平距离 / 日波动 | 每日强平率 | 每步强平率 | 每日穿仓率 | 穿仓间隔 |
|---|---|---|---|---|---|
| Spacer | 1.02x | 2.9% | 0.15% | 0.32% | 每 16 游戏日 |
| Standard | 0.68x | 8.0% | 0.42% | 2.04% | 每 2 游戏日 |
| Medieval | 0.48x | **51%** | 3.5% | 3.13% | 每 2 游戏日 |
| Tribal | 0.35x | **92%** | 12% | 7.29% | 每 1 游戏日 |
| Raider | 0.30x | **98%** | 18% | 17.8% | 每 0.6 游戏日 |

**在 Raider 上开 100x，基本等于把钱直接送给平台** —— 每处理一次报价就有 18% 概率被强平。

这是**刻意保留**的结果：本模组的核心乐趣是"梭哈百倍杠杆"，
所以选择让 100x 全档开放，而不是把它锁死。想稳一点就降杠杆：
20x 下强平距离 2.5%，各档每日强平率只有 0.1% ~ 1.6%。

下单面板会在**强平距离小于日波动时显示橙色高风险提示**，
写明具体数值（如"强平距离 0.50% 小于日波动 1.68%，仅 0.30 倍"）。

> 早期取过 `StopOutVolCoverage = 1.0` 和 `0.6`，两者都把高波动档压到 20~50x，
> 使百倍杠杆形同虚设。那是"真实平台"的思路，不是这个 mod 的初衷。

### 时间换算

**一律引用原版常量，不自己推导。**

| 常量 | 值 | 来源 |
|---|---|---|
| `FxGameComponent.TicksPerDay` | **60000** | = `GenDate.TicksPerDay` |
| `FxGameComponent.TicksPerHour` | **2500** | = `GenDate.TicksPerHour` |
| `FxGameComponent.TicksPerRealSecond` | 60 | 1x 速度下 1 现实秒 |

#### 结算倒计时用 `GenDate` 恒等式

结算点恒在整日边界（`TicksAbs` 是 `GenDate.TicksPerDay` 的整数倍），
而原版时钟显示的就是 `GenDate.HourOfDay(TicksAbs)`。所以：

```
距下次结算小时数 = 24 − GenDate.HourOfDay(TicksAbs)
```

这是**恒等式**，不可能与游戏内时钟脱节 —— 两边读的是同一个值。

> **这个功能我错了三次，值得完整记下来。**
>
> 1. `(nextSettlementTick − TicksAbs) / TicksPerStep` —— 把报价步长当成了小时。
> 2. 改用 `TicksPerHour`，但那个值是我按 `TicksPerDay / 24` 推的，
>    而 `TicksPerDay` 本身就是错的。
> 3. 直到反编译 `RimWorld.GenDate` 才发现真值：
>    `TicksPerDay = 60000`、`TicksPerHour = 2500`，而我写的是 3600 / 150。
>
> 教训不是"某个常量写错了"，而是：**凡是原版已经定义的时间常量，
> 就不该自己推。** 现在代码里这两个值直接引用 `GenDate`，
> `Docs/audit.py` 也会核对。

可以在模组设置里打开 **「显示时间诊断行」**，结算倒计时下方会直接列出
`TicksAbs / 当前第几时 / 距结算 tick`，方便当场核对。

#### 关于倒计时跌得太快

如果看到倒计时在很短时间里从 19 掉到 1，请先看诊断行：

- **18 游戏小时 = 2700 tick**
- 1x 需要 **45 现实秒**；3x 需要 15 秒；5x（superfast）需要 11 秒

所以这个跌幅在一分钟内完成，说明当时是 2x 或更高速度，而不是 1x。
诊断行里的 `TicksAbs` 会随速度成比例增长，可以直接验证。

### 跳空与穿仓（负余额）

行情会**跳空**：低概率的单步大幅移动，可以直接越过强平线。

| 档位 | 每步概率 | 每游戏日 | 幅度（× 单步波动） |
|---|---|---|---|
| 常规跳空 | 0.20% | 约 3.9% | 3 ~ 9 倍 |
| **极端跳空** | 0.005% | 约 0.1% | **14 ~ 34 倍** |

**只有极端跳空才可能造成穿仓。** 分两档是为了还原真实市场的结构：
跳空本身不算罕见，但"跳空大到让客户倒欠钱"是真正的尾部事件
（现实里的类比是 2015 年瑞郎脱钩）。如果只用一档大跳空，
实测会变成"每次强平都是穿仓"（每 1~2 游戏日一次）—— 那就不叫风险，叫必然。

#### 穿仓：欠款必须补上

当跳空让亏损超过**全部保证金**时，账户余额会被推成**负数**。这不是 bug，
而是刻意保留的真实风险：

- 账户区会显示红色欠款提示
- **无法开新仓**（开仓需要余额 ≥ 保证金 + 手续费）
- **无法提款**
- 必须往终端里存入白银把余额填回正数
- 发一封 `ThreatBig` 级别的「穿仓」信件，与普通强平区分开

#### 实测频率

| 档位 | 可用杠杆 | 每日强平率 | 每日穿仓率 | 穿仓间隔 |
|---|---|---|---|---|
| Raider | 10x | 1.69% | 0.095% | 每 **52** 游戏日 |
| Tribal | 10x | 0.94% | 0.092% | 每 54 游戏日 |
| Medieval | 20x | 2.60% | 0.132% | 每 38 游戏日 |
| Standard | 20x | 0.89% | 0.089% | 每 56 游戏日 |
| Spacer | 50x | 2.56% | 0.121% | 每 41 游戏日 |

**穿仓频率强烈依赖杠杆**（这是玩家自选的风险）：

| Raider 上的杠杆 | 每日强平率 | 每日穿仓率 | 穿仓间隔 |
|---|---|---|---|
| 1x | 0.00% | 0.0000% | 几乎不会 |
| 5x | 0.11% | 0.036% | 每 139 游戏日 |
| 10x（本档上限） | 1.74% | 0.080% | 每 63 游戏日 |

即：**低杠杆几乎不可能穿仓，把杠杆推到自己品种的上限才会遇到。** 这与现实一致。

> 跳空方向不偏（对数空间带均值回归），所以长期不会单边漂移。
> 已验证：20000 步后偏离起始价不超过 ±4.4%。

### 爆仓与穿仓

**强平线（Stop-Out Level）** 遵循真实海外 FX 平台的规则：
当**净值跌到已用保证金的 50%** 时强制平仓，**而不是等保证金亏光**。

> 真实平台的强平线普遍设在保证金水平的 **20% ~ 50%**，参照：
> [Axi](https://help.axi.com/zh-TW/axiv2--axicorp-prod/article/auEr1HqT-) ·
> [Pepperstone](https://pepperstone.com/) ·
> [IC Markets](https://www.icmarkets.com.au/)
> 早期版本是"亏到 0 才强平"，等于 0% 强平线 —— 既不真实，
> 也让玩家在最后阶段承担了本不该有的风险。取 50% 是三者中最宽松的一档。

- 强平时**退还剩余净值**到账户，损失的只是那 50% 保证金。
- 超额亏损由平台承担，殖民者**不会**欠款 —— 这就是"穿仓"的处理方式。
- 各持仓独立强平，一个品种爆仓不影响其他持仓。
- 强平立刻弹出 `MARGIN CALL` 信件，并给全体殖民者挂上 -16 心情。

### 预警：一个阈值，一次弹窗

| 健康度 | 浮亏 | 行为 |
|---|---|---|
| ≤ **0.60** | 40% | **强制暂停**并弹出预警窗口（每个持仓只弹一次） |
| ≥ 0.50 | — | 强平（Stop-Out Level，退还剩余净值） |

反弹回 0.60 以上会复位，将来再跌破会**重新提醒一次**。

> **健康度和"浮亏百分比"要分清**（这里我以前也写错过）：
> 健康度 = 净值 / 原始保证金，所以 健康度 0.60 ⇔ **浮亏 40%**。
>
> ── 为什么去掉了"多档复燃" ──
> 早期是"0.80 起提醒，之后每跌到上次水位 × 0.6 就再提醒一次"。
> 结果是 0.80 → 0.76 → 0.75 → … 一路弹七八次，感受就是"掉到 76 弹一次、
> 掉到 75 又弹一次"。这属于**用连续机制表达离散意图**的错误 ——
> 玩家真正需要的信息只有一条："快被强平了"。所以现在就是一个阈值、一次弹窗。
> 相关的 `WarnThreshold` 与 `RearmFraction` 常量已删除，
> `Docs/audit.py` 会检查它们**不会复活**。

`Docs/audit.py` 还强制检查不变量 `CriticalThreshold > StopOutFraction`，
否则强平会先于预警发生、预警永远不触发。

### 最小持仓：同一报价步内不能平仓

**持仓必须至少跨过一次报价才能平仓。** 在同一个报价步内平仓，订单会被**作废并全额退款**
（含开仓手续费），不产生盈亏。

覆盖两种情况：

1. 游戏**暂停**时 `TicksGame` 不前进，所有操作落在同一个 tick；
2. 时间流动但**还没跨过下一次报价** —— 价格未变，瞬时往返没有依据。

未跨过报价的持仓，平仓按钮会置灰并提示原因。

> 这条规则是为了封死一条真实的刷钱路径。真实平台对超短线往返也有惩罚，
> 所以它同时也是一条可解释的玩法规则，而不只是补丁。

### 盈亏方向（曾经的严重 bug）

`entryRate` / `markRate` 存的都是"方向价"（做多看 ask/bid，做空看 bid/ask），
**但它们本身不带方向符号**，所以 `Pnl` 必须按方向翻转：

```
做多：units × (markRate - entryRate)     价格涨 → 赚
做空：units × (entryRate - markRate)     价格涨 → 亏
```

这里**曾经写成无方向的 `markRate - entryRate`**，后果很严重：

| 方向 | entry | mark | 无方向减法 | 结果 |
|---|---|---|---|---|
| 做多 | ask | bid | **负**（entry > mark） | 看起来正常 |
| 做空 | bid | ask | **正**（entry < mark） | ❌ **开仓瞬间白赚一个点差** |

于是"做空 → 平仓 → 做空 → 平仓"就是一台印钱机：
每次开仓凭空得到一个点差，平仓立刻锁定。

**症状**：做空时价格**上涨**反而盈利，盈利额恰好等于 `点差 × 数量`。
实例：Credit/XAG，10000 单位，115.66 → 117.32，100x，刷出 16631。
修正后同一笔交易正确算出 **−16600**。

`Docs/verify_spread.py` 的**验收 9** 锁死这个行为，包含：
四个方向/涨跌组合、以及"开仓瞬间两个方向都必须亏一个点差"。

## 心情：按平仓，不按日

> 这一节在 2026-10-17 被**整节重写**。旧版本是"按当日盈亏挂一个档位、阈值写死 ±400/±40"，
> 已被完全替换 —— 旧方案有两个硬伤：
> **① 阈值是绝对值**，账户一大就天天"平淡"，系统自己失效；
> **② 一天只结算一次**，体现不出"这一笔亏得有多惨"，而那恰恰是玩家在意的。

### 十档

**每一笔平仓**都按该笔盈亏记一档。金额为 0 不记（既不赚也不亏，硬塞进任一边都是失真）。

| 档位 | 区间（白银） | 每层心情 | 时长 | 叠加上限 |
|---|---|---|---|---|
| **巨亏** | ≤ −10000 | −15 | 1.0 天 | 3 |
| **大亏** | −9999 ~ −5000 | −10 | 0.85 天 | 3 |
| **中亏** | −4999 ~ −1000 | −7 | 0.65 天 | 3 |
| **小亏** | −999 ~ −1 | −5 | 0.5 天 | 3 |
| **小赚** | 1 ~ 999 | +3 | 0.5 天 | 3 |
| **中赚** | 1000 ~ 4999 | +5 | 0.65 天 | 3 |
| **大赚** | 5000 ~ 9999 | +8 | 0.85 天 | 3 |
| **巨赚** | ≥ 10000 | +12 | 1.0 天 | 3 |
| **爆仓** | 强平触发 | −20 | 1.0 天 | 3 |
| **穿仓** | 余额被推成负数 | **−28** | 1.0 天 | **1（不叠加）** |

**阈值刻意用绝对白银数**，不随账户规模缩放 —— 玩家能直接理解"亏了一万"是什么概念，
百分比反而抽象。

### 叠加与共存

**最多同时挂 3 条**。同一档再来一笔就**叠层**（描述逐层升级）；不同档各自占一条。
挂满后新档**挤掉最早的那条**（先进先出）—— 这样最新发生的事永远看得见。
否则你亏了一万，屏幕上却还挂着三次"亏了五百"，很荒谬。

叠层会同时放大**数值**（×层数）与**时长**（每层 +25%，封顶一天）。

**穿仓不叠加**：它本来就要等极端跳空（日概率约 0.1%，约 1000 游戏日一次），
叠三层是 −84 —— 那不是"更难过"，那是直接删档。

**穿仓顶掉爆仓**：两者是同一件事的两个严重程度，同一账户不可能同时"爆仓"又"穿仓"。
若都挂，一次事故吃两份心情（−20 −28 = −48），那不是更真实，只是更狠。

### 时长是自己算的，不能靠原版

> **⚠️ 这里踩过一个坑，值得单独记。**
>
> `Thought.DurationTicks` **只对 `Thought_Memory` 生效**。
> 本系统用的是情境想法（`Thought_Situational`），原版**根本不读它的时长** ——
> 情境想法靠 `CurrentStateInternal()` 每 120 tick 重算来决定去留。
>
> 最早我覆写了 `DurationTicks`，**结果想法永远不会消失**（玩家能一直看到它挂在需求页）。
>
> 正确做法：条目上记 `sinceTick`，worker 自己比对时长，超时返回 `Inactive`。
> 叠层会刷新时刻，所以"反复小亏"不会因为每笔都轻就一闪而过。
>
> 代价：**不会显示原版那种"消逝于 x 小时"**（那是记忆想法专属的）。
> 心情到点直接消失，实测 6:00 叠满三层的小亏在 23:00 消失，符合 0.75 天的设定。

### 强度可调

模组设置 →「平仓心情强度」三个滑块（0 ~ 2×）：

| 滑块 | 覆盖面 |
|---|---|
| 亏损心情倍率 | 巨亏 / 大亏 / 中亏 / 小亏 |
| 盈利心情倍率 | 小赚 / 中赚 / 大赚 / 巨赚 |
| 爆仓心情倍率 | 爆仓 **与穿仓**（穿仓是更重的一档，−28，不叠加） |

调到 **0** 即关掉该类心情。基准值写在 `FxMoodSystem.TierMood`，滑块只做整体缩放 ——
不必逐档去调 10 个滑块。

### 文案的硬约束：必须能单独读懂

这些描述会被**单独喂给 LLM 对话模组**生成对白，所以每条都**自带完整语境**：
点明是外汇交易、点明方向、点明量级，**然后**才是画面感。

反例（已废弃）：单独一句"有人在打听沙发多少钱"会被 LLM 理解成殖民者想置办家具，
而不是刚赚了钱 —— 于是产生幻觉。现在写成"外汇上又一个几千的盈利。有人在打听沙发多少钱一张。"

## 图表叠加层

K 线图上会画三类横线，各自说明不同的东西：

| 线 | 样式 | 颜色 | 含义 |
|---|---|---|---|
| **开仓价** | 虚线 | 按方向（多绿空红） | 该笔持仓的方向成交价 |
| **盈亏平衡线** | 实线 | 蓝 | 中间价走到这里，该货币的浮盈浮亏归零 |
| **爆仓线** | 虚线 | 橙红 | 走到这里净值跌到保证金的 30%，会被强平 |

> **为什么做空的线在最新价下方**：K 线画的是**中间价 mid**，而 `entryRate` 是**方向成交价**。
> 做多吃 ask（高于 mid）、做空吃 bid（低于 mid），偏移恰好是半个点差。

### 爆仓线怎么算

强平判据是 `eq ≤ margin × StopOutFraction`，而 `eq = margin + pnl`、
`pnl = units × (mark − entry)`（多）。解出强平时的方向价：

```
mark* = entry − StopOutFraction × margin / units     （多）
mark* = entry + StopOutFraction × margin / units     （空）
mid*  = mark* / (1 ∓ 半价差)                          （还原成中间价）
```

**⚠️ 用的是含追加保证金的 `margin`** —— 强平判据用的就是它。
补保证金会把爆仓线推远，函数必须如实反映，否则玩家补了钱却发现线没动，
会以为补了个寂寞。

**用真实爆仓单验证过**：紫色B LONG 2457 单位 / 保证金 3356.26 → 算得强平价 133.1085，
实际强平时 `exitRate = 133.0078`（已跌破）。4 笔实盘强平单全部对得上。

### 线跑到坐标轴外时画边缘箭头

> 这是"做空**有时候**看不到爆仓线"的真因。
>
> 爆仓线距现价只有 **0.35%**（0.5 / 杠杆），而可视窗口半宽约 0.85% ——
> 价格落在窗口上/下方约 1/3 区域时线就出界了。
> 做空时爆仓线在**上方**，而做空通常是因为价格在涨（现价偏高）→ **经常撞上界**。
> 做多对称，只是方向相反。窗口随 K 线滚动，线就时显时隐。
>
> 修法：出界时**不消失**，改在对应边缘画箭头 + 距离读数（如「爆仓 87.10（在框外 +0.44%）」），
> 明确告诉玩家"线还在，只是在上/下方"。

### 文字避让

图表上有四个固定元素会互相抢位置：回本线标签（左上）、持仓线图例、
「显示 N 根…」（底部）、爆仓线标签。为此有一个统一的布局函数：

```csharp
/// 给定期望位置，返回一个不与既有元素重叠的 y
private static float ReserveLabelY(Rect area, float want, params float[] extraTries)
```

三级策略：**期望位置 → 候选位置 → 逐像素扫描兜底**。

> **这个坑我踩了两次**：先给爆仓线标签写了避让，后来加边缘标记时**没复用**，
> 同一个 bug 又出现（文字压在底部图例上）。根因是保留区当时是各写各的局部变量，
> 新代码天然会绕过它。现在集中在一处，谁要放图表文字都走这条路径。

## 测试专用板块

模组设置**最上面**有两个按钮，专门覆盖"必须验证但正常游玩验不到"的路径。

| 按钮 | 作用 |
|---|---|
| **① 加一层「小亏」心情** | 每按一次给当前地图全体殖民者叠一层小亏。用来验证叠加与跨日过期 —— 小亏时长 0.5 天、叠满 0.75 天，睡一觉就该消失。 |
| **② 安排一次极端跳空** | 约 **3 游戏时**后所有货币发生一次最大档向下跳空。先用百倍杠杆做多以测试穿仓。**只触发一次。** |

**为什么需要它**：
- 心情叠加/过期要跨游戏日才看得出来，正常玩一次要等十几个小时
- 穿仓要等极端跳空，日概率约 **0.1%** —— 约 1000 游戏日才碰上一次

**跳空为什么延迟 3 小时**：玩家需要时间去梭哈百倍杠杆做多。立刻触发就来不及建仓，
测不到想测的东西。

**跳空为什么固定向下**：测试流程是"百倍杠杆做多"，只有向下跳空才会穿仓。

**幅度为什么是 60~120σ**（而不是常规的 14~34σ）：

```
100x 多仓亏损占保证金的比例 = 杠杆 × 价格跌幅
```

要 > 1（穿仓）就需要跌幅 > 1%。实测最稳档（vol 0.35）在 **34σ 时只跌 0.91%** ——
亏 91% 保证金，**还差一点，测试会"看起来失败"**。60σ 才稳（跌 1.60%）。

## 强平的手续费口径

> 2026-10-16 修。这是从**导出真实交易记录核对**才发现的 bug。

早先强平路径写的是：

```csharp
float refund = eq;                    // 不扣平仓费
totalFee = pos.openFee,               // 只记开仓费
```

而手动平仓写的是 `equity - fee` 和 `pos.openFee + fee`。后果：

- **被强平反而比主动平仓更便宜** —— 方向完全反了
- `totalFee` 混了两种口径，报告不可信

**实测 4 笔强平单**，手续费恰好等于开仓费（65.75 / 138.50 / 321.72 / 547.14），
**合计漏收约 1289 白银**。

现在两条路径完全对称：平仓价取 `markRate`，手续费按下单名义计收（下限 `MinFee`），
实际到账 = 净值 − 平仓费。**顺带把穿仓判据也改准了**：原来用 `eq < 0`，
现在用 `acc.balance < 0`（扣费后的余额才是账户的真实状态）。

## 报告里的 totalPnl 是毛盈亏

导出的交易报告头里：

```
totalPnl        逐笔 pnl 之和，【未扣手续费】
totalFee        手续费单独一列
```

所以 `totalPnl` 不等于实际净赚，**净额要自己减 `totalFee`**。
（这一条在核对时确认过：`sum(pnl) = 15530.49` 与报告头吻合，而 `sum(pnl) − sum(fee) = 13832.36` 不吻合。）

另外 `pnl` 与 `units × (exitRate − entryRate)` 会有**分位级差异**（最大约 0.006%），
那是 float 存储精度，不是公式错误 —— **以 `pnl` 列为准**。

## 设计说明

### 货币如何生成

每个非玩家、非隐藏派系在首次接触市场时**确定性生成**一种货币：

- 种子 = `派系 loadID × 7919 + 104729`，因此同一存档里货币名称和符号稳定不变。
- **部落派系**（科技 ≤ 新石器）用贝壳 / 珠子 / 琥珀一类名称，汇率区间 20–140。
- **其他派系**用信用点 / 元 / 马克一类名称，汇率区间 5–260，有概率带上企业名（如 "Vega Credit"）或派系名。
- 符号取名称首字母 + 由 loadID 派生的字母（如 `VCK`）。

### 汇率模型：多尺度均值回归堆栈

> 2026-10-16 从"单 OU + 正弦锚"换成**五级 OU 堆栈**。原因：
> 单尺度下噪声的相关时间只有 25 步（≈75 现实秒），**不到 2 根 K 线就衰减掉 60%**，
> 可视窗里只剩"底色"，没有任何可持续的段落 —— 图上就是一条规整的尺子。

**唯一必须守住的不变式**：

```
Σ_k  2σ_k²/(2−θ_k)  =  σ_step²  =  DailyVol² / StepsPerDay
```

**把预算按尺度重新分配，总量一个字节都不多。** 所以日波动率仍恒为 `DailyVol`，
点差 / churn / 杠杆上限等全部经济验收的依据不变。

五级尺度（τ 单位：游戏日）：

| τ | 角色 | σ_k/σ_step | 占预算 |
|---|---|---|---|
| 2 小时 | 点差 / churn 依赖的噪声底 | 0.079 | 0.6% |
| 8 小时 | 盯盘时看到的分钟级往复 | 0.158 | 2.5% |
| **1 日** | **可交易的波段**（原来最缺的一档） | 0.273 | 7.5% |
| **3 日** | 趋势 | 0.473 | 22.4% |
| **9 日** | 大级别方向（取代原正弦锚） | 0.819 | 67.1% |

**实测**：`Σ 步位移方差 / σ_step² = 1.000560`，误差 **0.056%**。

### 为什么换掉正弦锚

试过四种"加趋势"的方案，前三种全部失败（记录在案，别重蹈）：

| 方案 | 步级 σ 放大 | 自相关 | 为什么失败 |
|---|---|---|---|
| 慢速 EMA 锚 | — | −0.0004 | θ/α 差 18 倍，锚每移动一点价格 17 步内就跟上并抹平 |
| 随机趋势项 | 1.14 ~ 4.6 | −0.035 | 均值回归把随机趋势吸收成噪声，稳态贡献 ≈ 17.7× |
| 锚做随机游走 | 1.0000 | −0.039 | gap 方差被 θ 锁死，价格只是「锚 + 固定偏移」 |
| 确定性正弦锚 | 1.0006 ~ 1.0158 | +0.05 ~ +0.125 | 可用，但**严格周期**、太机械 |

**根本矛盾**：随机过程里"步级噪声"与"窗口级趋势"由**同一个 σ** 绑定，
所以任何**随机**趋势项都必然抬高步级方差 —— 而那是点差/churn 经济验收的基石。

正弦锚是唯一不抬高方差的方案，但它是**严格周期**的：每个货币的模式固定且精确重复，
玩久了会看出"这个币每 6 天走一个来回"，像钟摆而不像行情。

**多尺度 OU 解决了这两点**：最慢那一级承担趋势，因为是**多级叠加**，
合成波形在很长时间内不会重复；而且它**计入方差预算**，账目上比正弦锚更干净。

### 两个滑块控制最慢那一级

| 滑块 | 控制 | 效果 |
|---|---|---|
| **慢周期行情强度** | 它的**权重** | 0 → 趋势占预算 **0%**（真关掉）；0.08 → **89%** |
| **慢周期长度** | 它的 **τ** | 1 日 → 占 25% 预算；60 日 → **95%** |

**缩放后重新归一化，所以两个滑块只重排比例、不加总量**（实测总预算恒为 1.000x）。

> **这两个滑块曾经是死的。** 正弦锚被多尺度 OU 取代时，我删了调用点却留下了设置项，
> 于是**玩家拉滑块什么都不会发生** —— 那比死代码更糟，是在骗人。
> 现在它们真的接进了 `AllocateOscBudget`，而且 `EnsureOsc` 会在滑块变化时自动重建。
> `Docs/audit.py` 专门加了一条检查防止再出现死控件。

### 盘内路径（振荡子池）

每根 K 线内部走 16 个子步。路径形状从**按步轮换的 8 条振荡子**里取。

> 早先用的是**全局唯一**的静态桥 —— 后果是**所有货币、所有 K 线的盘中路径完全相同**，
> 影线的纹理是假的。这是"规整感"的一个真实来源，已修。

每条振荡子都是**两端钉零**的布朗桥。钉零是硬要求：它保证
`log(rate) @ k=N == stepLogTarget` **逐点相等**，步边界分布不被盘内路径影响。
曾经用单端桥，实测让 K 线实体凭空胖 **7.9%**。

### 存档兼容性

所有状态挂在 `WorldComponent`（`FxGameComponent`）上，随存档持久化：
汇率市场、各货币汇率与锚价、殖民地账户、所有持仓、上次结算盈亏。

⚠️ **Alpha 阶段字段还会变**。如果你在开发过程中存了档，之后新增/删除
`ExposeData` 里的字段可能导致读档异常。建议开发期用新开局测试。

## 踩过的坑（改这个 Mod 时请注意）

1. **建筑 def 必须自带 `graphicData`**。`ThingDefGenerator_Buildings` 会为可建造建筑派生
   蓝图/框架 def，靠 `GraphicData.CopyFrom` 复制原 def 的图形数据；缺失会让整个 Def
   加载阶段崩溃（`NullReferenceException`），游戏会重置 mod 列表并放弃加载。
2. **不可搬运的建筑不要写 `thingCategories`**。判定条件：
   `category == Building && !Minifiable && thingCategories 非空` → 配置错误红字。
3. **Keyed 文本必须放 `Languages/<语言>/Keyed/`**，不能放 `DefInjected/Keyed/`。
   `DefInjected` 下的每个子目录名都会被当作 Def 类型名解析，`Keyed` 不是 Def 类型，
   会触发 `dir doesn't correspond to any def type` 语言加载错误。
4. **占位符可以按语序重排**（如中文用 `{1} {0}` 是合法的），
   但占位符集合必须与调用方一致。
5. **🔴 不持久化的运行时字段，默认值必须"安全"——否则读档即崩价。**
   这是迄今最严重的一次回归（2026-10-16，步内子采样引入）：

   `stepLogStart` / `stepLogTarget` 是每步现算的运行时字段，**不进存档**，
   读档后回到默认值 `0`。而价格是这么算出来的：

   ```csharp
   logMid = stepLogStart + (stepLogTarget - stepLogStart) * t;   // 全是 0 → logMid = 0
   rate   = Clamp(Exp(logMid + bridge), MinRate, MaxRate);        // Exp(0) = 1
   ```

   **`Exp(0) = 1`，而 `MinRate` 恰好也是 `1`。** 于是读档后第一次推进子步，
   所有货币瞬间被打到价格下限，然后靠均值回归慢慢爬回锚点 ——
   玩家看到的就是"每次读档所有货币跌到极低价，再慢慢涨回来"。

   （当时用的是单 OU，所以爬回去靠的是那个 `MeanReversion` 回归项；
   现在换成多尺度堆栈后，回归来自各级 OU 自身的衰减项，但**这个坑的本质不变**：
   读取一个默认值为 0 的运行时字段，代入 `Exp()` 会算出 1，而 1 恰好是价格下限。）

   时序上很容易漏掉：读档后**第一帧** `lastStepTick` 才被设为当前 tick（欠 0 个子步，安全），
   但**第二帧**欠 1 个子步就会调 `AdvanceSubSteps` —— 此时还没有任何 `TickStep` 跑过。

   **修法**：加 `stepBudgetValid` 标志，并且**在"写"和"用"两侧都设防**：
   - `TickStep` 与 `BeginStepBudget` 建立预算时置 `true`
   - `AdvanceSubSteps` 跳过未建立预算的货币
   - `AdvanceSubStep` 内部再挡一次（崩价代价太大，值得两道防线）

   **通用教训**：新增运行时字段时，先问一句"它的默认值代入公式会算出什么"。
   默认 `0` 经过 `Exp()` 会变成 `1`，经过乘法会变成 `0`，经过除法会变成 `∞` ——
   三者都可能落在合法区间内，从而**静默产生一个错误但看起来合理的价格**。
   `Docs/audit.py` 已加 4 条回归检查（预算检查、二次设防、建立点、禁止持久化）。
5. **`Window.forcePause` 默认为 `false`**，自定义窗口不会暂停游戏。
   游戏的强制暂停判定是 `TickManager.ForcePaused`，读的是
   `Find.WindowStack.WindowsForcePause`（任一窗口 `forcePause=true` 即为真）。
   如果哪天想改回暂停，把这个字段设成 `true` 即可。
6. **不要在 `DoWindowContents` 里 `new` 列表给图表用** —— 它每帧都跑。
   当前 K 线每帧构造 `GetCandles(...)` 的小列表（约 60 个元素），
   对单次绘制可接受；若要支撑长周期或大量货币，应改为缓存。
7. **采样挂在 `WorldComponentTick` 上**，它只在模拟推进时被调用，
   所以暂停时天然不推进、加速时自动变密 —— 无需任何暂停检测代码。
8. **`SetInitialSizeAndPosition()` 会被 `PreOpen()` 调用**，
   在构造函数里改 `windowRect` 会被覆盖。要调窗口初始位置必须重写这个方法。
9. **`absorbInputAroundWindow = true` 会挡住窗口外的点击**（包括原版时间控制）。
   本模组设为 `false`，同时在窗口内嵌了一份原版时间控制。
10. **`TimeControls.DoTimeControlsGUI(rect)` 可安全内嵌**，它用 `Widgets.BeginGroup`
    相对传入 rect 绘制，并自带快捷键 tooltip。宽度需预留 `TimeButSize.x * 4`
    （四档速度按钮）。
